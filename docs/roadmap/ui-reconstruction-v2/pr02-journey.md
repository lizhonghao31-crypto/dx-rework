## 公共契约与 API

`@dx-rework/contracts/digital-production-journey` 提供七大流程、全部小流程稳定 key、名称、进度计入标记、节点/订单 DTO、筛选和返回参数。API 仅适配既有任务 kind（外厂裁映射整款开裁），不创建另一套状态机。

| 入口 | 输出 |
| --- | --- |
| GET `/digital-production/journeys` | 权限范围内同一快照的 KPI、总数、20条分页列表 |
| GET `/digital-production/journeys/export` | 相同筛选、权限、规则和快照的全部匹配记录；无分页字段 |
| GET `/digital-production/journeys/:id?round=N` | 来源或母单 ID 的单一档案，指定轮次须有来源读取权限 |

接口沿用现有数字生产认证、功能开关，响应 `no-store`。每次查询使用 `REPEATABLE READ READ ONLY` 和一个 `asOf`；只读 PostgreSQL 事务阻止写入。导出和列表使用同一选择函数，不按节点重复计算订单。

搜索覆盖授权可见的客户、设计师、主/第二跟单、设计/正式/代用款号、款名、PO、母单/来源及关联记录 ID、原外发订单号。结构化参数包含客户、跟单 UUID、品类、大流程、小流程、状态、风险、KPI、创建日期区间（上海自然日）及页码。大流程、小流程、状态和风险须命中同一个当前节点。KPI 基于其它筛选后的授权范围；KPI 再筛选列表与导出。历史节点不会污染当前 KPI；`hitReasons` 列出命中的当前节点。

`journeyReturnUrl` 仅生成本站座舱路由，保存以上筛选、page、selected、expanded；未知参数拒绝。具体页面如何恢复上下文由后续消费 PR 实现。

## 显式身份与领域事实

| 流程 | 唯一事实/入口来源 |
| --- | --- |
| 订单创建 | digital_production_sources/orders、原开发发布事实、PO/尺码订购信息 |
| 产品开发打板 | 原开发文档、轮次、任务/前置/事件、工资原关联；沿用显示 inherited |
| 大货产前准备 | 原客户样板判断、预算发布版本、外发 IE/总监/老板审批快照、制单版本、纸样/唛架和预缩事实 |
| 订单开裁 | 原 bulk task 与 child_links/child_lines 的 PO 实裁关联；未齐全部 PO 不算整款完成 |
| 裁后工艺与发厂 | 原工艺/QC/发厂任务及 factory facts；无二次工艺显示不适用 |
| 工厂生产 | 原到料事实、清点/船样任务、生产填报状态迁移；业务日期不伪造成精确完成时间 |
| 回货与装箱 | 原 OrderClosureService 实收/更正/装箱/差异、返工/尾查报告/整单复核/责任事实、特殊结案 |

所有跨模块匹配使用来源、母单、轮次、版本、PO line UUID 与显式 child_links/child_lines。款号只能搜索。来源先行、确认母单后保持来源档案 ID；直接订单先行、后附来源时依据原 `digital_source_attached` 审计保持母单档案 ID。两种 ID 都能解析同一档案。补正式号或读取历史不会生成任务、实绩、工资或另一份数量账。

开发进度直接读取原 `routeProgress`；大货进度复用原 `bulkCockpitProgress`。唛架可独立展示，分母不另加一。物料退回的原任务留历史，原复核接续适用节点。当前有效制单、采用开发轮次、产前 route 与历史实例分开；正常装箱完成和特殊结案沿用原规则。

开裁展示复用 `BulkPreparationService.gates`、原开裁任务生成事实及纸样/唛架、预缩完成条件；仅用于说明缺项，不构成新放行。纸样/唛架与预缩并行、外发批准在开裁前；不增加财务放行或审批。

## 权限与时间

原 resource policy 决定档案范围；当前任务主办仅获得自己的任务元数据，原 task/业务处理权限继续检查。新接口不放大已知 A4 同母单任务元数据缺陷；旧接口未在本 PR 修改。外发、预算、生产、返工原入口继续按对应权限/范围决定是否提供 URL，预算金额和责任金额不进入 Journey。

完成主办、实际操作者、原改派审计分别返回。预期时间只复用原有效 SLA deadline；未进入保持 `not_started`，未设 SLA 为 `not_set`，未生成为 `uncreated`，待前置为 `pending`。实际时间只读原完成事实，补报未核实单独标识。缺实际时间或缺目标时完成结果为 unknown；不用登记时间、当前时间补造。无权限用 `unavailableReason=permission`；原域未记录独立事项事实用 `fact_not_recorded`。

以下原数据限制需在阶段确认时说明：未生成节点尚无独立计划日期；唛架完成仅有登记时间，原生产完成仅有自然日；部分质检/责任事项没有独立精确完成时间。PR02保留空值和对应状态，未替业务负责人制定默认计划、SLA或推导责任人。部分旧关联模块没有支持准确子记录的 UI 路由时 URL 为 null，保留真实 ID；不替换成模块首页。

列表为同一事务内的领域事实投影；目前逐档案调用原领域读取，正确性优先，尚未进行大规模数据量的负载验收。后续上量前须以真实规模验证时延，不能把测试小数据下通过称作性能验收。

## 验证与边界

- 专项 PostgreSQL 使用完整原 migration manifest 的独立临时 schema，覆盖两 PO、来源/直接订单两种起点、相同后四位负例、权限正反、并发确认、补号及只读查询不产生任务/工资。
- 原真实业务链增加 Journey 对照：局部 PO 回货、重复实收、完整装箱、当前/历史开发轮次、沿用和工资原计数。
- 单元测试覆盖同节点组合筛选、订单去重、分页/导出/KPI同源、完成时间质量和安全返回参数。
- 前端只验证新增历史预算只读参数及收货定位，未进行 PR03–06 页面视觉施工。
- FULL Gate 与一次 GitHub Codex Review 必须以最终 intended HEAD 为准，交付报告单列其结果。

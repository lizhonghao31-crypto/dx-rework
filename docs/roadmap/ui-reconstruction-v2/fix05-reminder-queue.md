# FIX-05 提醒队列与待办边界

依据：2026-10-06 第一阶段用户确认：点击“我知道了”确认当前提醒后立即显示下一条；减少的只有“还有 X 条待办提醒”，我的待办按实际业务完成情况变化。基线为已合并 FIX-04 的 release/digital-production-v1；关键通知链路使用 FULL 和一次 GitHub Codex Review。

remainingCount 是当前用户仍有效、尚未显示且未确认的提醒数，不包含当前已经显示的提醒；继续逐项使用原通知有效性、原主办 / 代理、角色与资源权限校验。业务 TODO 统计和原任务完成服务不变。没有加入新的待办数量来源，没有把 receipt 的 shown / acknowledge 变成业务完成，也没有重放已经展示过的提醒。

新前端以 remaining=1 请求可选的计数。旧调用保留原严格 notification 响应，新的计数字段为可选；新页面遇到旧 API 未提供该字段时隐藏计数。原 claim 的原子收件游标、同屏一个提醒和去处理 / 查看导航继续保留。确认后刷新下一条，迟到的旧响应不能恢复已确认提醒。

桌面弹窗在原色系中收紧宽度与留白，字号保持至少 12px。手机保持 16px 和 44px 按钮，输入时隐藏，继续按实际可见操作按钮测量避让；长款号使用原资源资料，允许换行和内部滚动。

验证计划：原 PostgreSQL 通知回归，新增有效 / 失效队列计数、跨用户拒绝、2→1→0、确认幂等、我的待办仍为 3 以及原业务真正完成后变为 2；实际普通设计师桌面 / 手机通过原核配退回创建三条补料待办并验证即时切换。最终 SHA、视觉、旧模块、门禁与 Review 结果记录于 PR。只使用隔离本地新 TEST 记录，不部署、不执行线上 SQL、不操作真实订单，不处理本阶段外的仓库入口 / 板房元数据旧缺陷。

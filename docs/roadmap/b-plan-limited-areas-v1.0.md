**核心约束：** **保留原有工作区域，不整体重构业务办理区；只改分析区、筛选区、入口区、明确点名页面和新增能力。**

## 0. 本轮目标

本轮不是“全系统换皮”，也不是继续增加展示框，而是完成四件事：

1. **保护原工作区**
   - 收货、多次收货、补录、返工节点办理、工人报数、IE核价、判责、扣款、样衣借还/处置等原工作区域不整体重排。
   - 原来点击进去是什么业务逻辑，改后仍保持相同业务逻辑。
   - 分析功能失败不得阻断业务办理。

2. **把展示型分析升级为业务闭环**
   - 从“展示数字”升级为：**识别问题 → 排序优先级 → 下钻原单 → 进入原办理入口 → 处理后自动回读结果**。
   - 不建立第二套业务表单，不要求一线重复录入。

3. **统一限定区域 UI**
   - 统一分析入口、展开区、筛选区、洞察摘要、工具栏的间距、对齐、按钮层级与信息密度。
   - 不通过全局 CSS 重做全站，不污染稳定工作区。
   - 保持现有蓝/白/深色导航体系和工业化、紧凑风格。

4. **补齐本轮明确缺口**
   - 收货差异/装箱差异现有“去处理”弹窗增加图片上传及回看。
   - 供应商目录/资料维护真正分离；资料维护增加批量录入。
   - 流程等待增加搜索、节点提交人及业务洞悉。
   - 返工详情增加返回；“工资基础”改成清晰业务口径；补齐订单级重新判责。
   - 实时看板移除碍事框；Root 增加订单行删除/排除入口。
   - 回货分析并入原看板筛选与异常视图。
   - 样衣筛选去掉多余二层折叠。
   - 移动端返工改成真正的移动布局。

# 2. 限定区域统一 UI 规则

## 2.1 统一结构

分析类区域统一：

```text
原页面标题 / 原工作区
↓
紧凑分析摘要条（默认收起）
↓
展开后：分析工具栏
↓
洞察摘要
↓
异常/分析列表
↓
口径与历史说明（最低视觉层级、默认折叠）
↓
原工作区保持原样
```

禁止：

```text
大白框
 └─ 第二个大白框
     └─ 第二层筛选折叠
         └─ 指标框
             └─ 又一套重复列表
```

## 2.2 间距体系

限定区域统一使用固定节奏：

- 区块间距：**12–16px**
- 区块内部 padding：**12–16px**
- 同一行控件 gap：**8–12px**
- 标题与副标题：**4px**
- 洞察卡之间：**8–10px**
- 列表行之间：尽量使用边界线而非大片空白
- 同一级区域必须共享左右对齐线

禁止同一页面同时出现大量 20px、28px、35px 等随机间距。

## 2.3 容器规则

只保留三类：

1. **工具栏容器**：搜索、筛选、刷新、导出、设置。
2. **洞察摘要卡**：最多 3–5 个，只显示可行动指标。
3. **分析列表/异常列表**：一行一对象，支持点击下钻。

不再给每个数字、说明、按钮单独套 Surface。

## 2.4 按钮层级

- 蓝底主按钮：当前页面最主要动作，最多 1–2 个。
- 次按钮：白/浅底，用于刷新、清除、展开等。
- 低频设置：图标/弱按钮，放右侧。
- 危险动作：红色文字/红边，但保持小尺寸。
- “去处理”“录入”等行内按钮继续保持紧凑小按钮，不扩大成大 CTA。

## 2.5 展开区

收起态不再只有“XXX·展开”，而应显示摘要：

```text
流程等待与往返   当前等待 12   有往返 3   时间缺失 1                   展开⌄
```

展开后：

```text
[搜索] [节点] [等待范围] [异常类型] [刷新]
[当前等待] [长时间停留] [反复退回] [时间缺失]
[分析列表]
[口径说明⌄]
```

**不再二层套“筛选记录范围”。**

# 3. PR01｜收货差异/装箱差异现有“去处理”弹窗增强

**目标：** 不新增新的差异处理模块，只增强现有两个“去处理”按钮。

- 装箱差异 → 去处理
- 处理结果文字
- 自动记录处理人
- 自动记录处理时间
- 保存后显示“已处理”
- 处理记录保持审计不可随意覆盖

**这些全部保留。**

## 3.2 本轮新增

### 图片上传

处理弹窗增加：

```text
收货差异 去处理

款号              BOxxxx
送货单数量        1,200
累计实收          1,180
当前差异          -20

处理结果
[                                         ]

处理凭证
[ + 上传图片 ] [缩略图] [缩略图]

处理人            张三（自动）
处理时间          2026-09-10 15:xx（自动）

[取消]                              [提交处理]

规则：

- 处理人、处理时间仍由系统按真实登录人和提交时间自动生成，**不允许人工伪造**。
- 无图片是否允许提交：建议**允许**，因为图片是增强证据，不应把已有可用流程突然变成强制上传；若业务后续要求必传再调整。
- 图片上传失败不得把已经成功的处理结果误显示为成功。

## 3.3 已处理回看 UI

处理凭证
[图1] [图2]
```

## 3.4 数据与审计

- 延续已有处理记录不可修改/删除原则。
- 新附件与 resolution 建立明确关联。
- 历史没有附件的记录正常显示，不补造空附件。
- 后续新收货/新装箱导致差异数变化时，不改写旧处理记录。

## 3.5 验收

- 无图提交、单图、多图。
- 图片上传失败。

- 原“去处理/已处理”按钮位置、颜色、大小不被破坏。

# 5. PR03｜供应商资料维护“批量录入” MVP

**目标：** 快速批量新增供应商，但不直接批量覆盖旧资料。

## 5.1 入口

仅资料维护页：

```text
[新增供应商] [批量录入]
```

仅沿用现有供应商资料维护写权限；不因批量功能扩大角色权限。

## 5.2 交互

采用 4 步小型工作区/弹窗：

```text
批量录入供应商

1 下载模板
2 上传文件
3 校验结果
4 确认导入
```

### Step 1 下载模板

标准 `.xlsx`。

字段与现有单个新增字段保持一致，例如：

- 供应商编码（可选/按既有规则）
- 供应商名称
- 供应商类型
- 启用状态
- 联系人
- 联系电话
- 地址
- 合同主体
- 乙方代表
- 收款人
- 收款账号
- 开户行
- 可承接工艺
- 常规日产能
- 备注

**银行账号必须按文本处理，禁止 Excel 科学计数法污染。**

### Step 2 上传

- 一次一个 `.xlsx`
- 不开放任意列名猜测
- 不自动修改原文件

### Step 3 校验

分三类：

**可导入**
- 格式合法
- 无明确冲突

**疑似重复/冲突**
- 编码与现有供应商冲突
- 同文件编码重复
- 名称+类型疑似已有

**失败**
- 必填缺失
- 类型非法
- 产能非合法整数
- 工艺空值/重复等

UI：

```text
可导入 42    冲突 3    失败 5

行 | 供应商 | 状态 | 原因
1  | XX制衣  | 可导入 |
2  | YY制衣  | 冲突   | 系统已有相同编码
3  | ZZ制衣  | 失败   | 联系电话缺失
```

### Step 4 确认

- 只导入“可导入”行。
- 冲突行不自动覆盖。
- 失败行不导入。
- 导入结果保留逐行结果。

## 5.3 一期明确不做

- 不做批量修改已有供应商。
- 不做“自动合并重复供应商”。
- 不做 ERP 同步。
- 不做复杂列映射器。
- 不通过批量导入绕过单条新增校验。

## 5.4 验收

- 标准模板。
- 银行账号长数字不丢精度。
- 供应商类型、工艺、产能校验。
- 同文件重复。
- 与系统已有编码冲突。
- 部分成功、部分失败。
- 重复提交幂等。
- 非维护权限用户不可调用后端导入接口。

**Gate：FULL**。  
**Codex Review：建议 1 次。**

- 提交时间

## 6.3 业务洞悉

系统不是只显示“12单等待”，而是产出以下**可行动分组**：

### A. 当前积压集中在哪个节点

```text
待责任判定  8单
待IE复核    5单
返工执行中  4单
```

点击数字直接筛出原返工单。

### B. 长时间未推进

不凭空建立员工 KPI。  
使用实际停留时长排序：

```text

BO2054xxx  N07  4天6小时
BO2054yyy  N06  2天3小时
```

若没有业务定义 SLA，只叫“等待最长”，不叫“超时违规”。

### C. 反复往返

识别明确的退回/重新提交链：

```text
2次以上往返  3单
```

展开显示：
- 哪个节点退回
- 谁提交
- 谁退回
- 原因
- 当前状态

### D. 数据完整性

进入时间缺失、历史节点缺失单独列示，不能把“没记录”当作“停留时间0”。

## 10.3 订单级“重新判责”

现有外部扣款台账里的重判能力保留，但入口不能只依附于供应商责任。

在返工详情“返工业务完成/责任结果”区域，为有权角色提供统一入口：

```text
重新判责
```

### 原则

重新判责不是修改旧历史，而是：

**新建责任版本，旧版本、原老板签字、原扣款记录全部保留。**

### 情形

#### A. 已完成但尚未发生扣款
- 允许发起重新判责。
- 填写原因。
- 回到 N07 责任判定。
- 新责任版本再次走老板确认。

#### B. 已部分扣款
- 已扣事实不删除。
- 新责任版本重新计算责任。
- 系统必须明确新旧责任与已扣款关系。
- 后续只处理剩余/调整差额，不能按新总额重复扣。

#### C. 已足额扣款
- 仍可在确有错判时发起，但必须明确进入“责任修订”。
- 不允许静默改旧账。
- 若新责任小于已扣，必须通过现有调整/冲销/后续明确规则闭环，禁止直接覆写。

#### D. 全本厂承担
- 不依赖供应商扣款 case 也能发起重判。

## 10.4 权限

- 继续沿用现有正式重判/判责相关角色边界。
- Root 保留全局调试能力。
- 不因增加订单级入口扩大普通角色权限。

- 全本厂责任重判。
- 外部责任未扣款重判。
- 部分扣款重判。

- 正常授权角色允许
- 非授权角色拒绝
- 前端隐藏 + 后端拒绝同时成立

## 15.4 数据

- 金额不丢精度
- 数量保持整数规则
- 统一千分位
- 金额最多3位小数的既有全系统规则不被破坏
- 审计历史不可被新功能覆盖

---

# 16. Gate 与 Review 原则

继续按仓库当前长期规则：

- migration/schema/金额/数量/责任/权限/审计/Root高风险操作 → **FULL**
- 纯限定 CSS/文案/布局且不触业务逻辑 → **QUICK**
- `[FULL]` 与 `[QUICK]` 互斥
- 先在本地完成定位和定向验证，再一次 push intended Head
- 不用 GitHub Actions 当调试器
- Codex 默认只 Review，不施工
- 默认每 PR 最多 1 次 Review
- PR08 重新判责属于高风险，必须 Review

---

# 17. 明确不在本轮范围

除非后续再次批准，本轮不做：

- 全系统重新设计工作区
- 全局组件库重构
- ERP 接入
- AI 自动判责
- AI 供应商评分
- 员工绩效评分
- 自创 SLA
- 预测性延期模型（在没有足够历史数据前）
- 供应商批量覆盖更新
- 样衣逾期自动提醒
- 新的财务月结状态机
- 任何未明确要求的角色权限扩大

---

# 18. 最终验收定义

本轮完成不是“UI变好看了”，而必须同时达到：

### 原工作保持稳定
业务人员仍能按原方式完成核心工作。

### UI 更紧凑
分析区域不再大框套小框，间距、对齐、入口一致。

### 数据产生行动
管理者能从系统直接看到：
- 应先处理哪张单
- 为什么
- 谁处理
- 点击哪里进入原业务流程

### 数据可追溯
洞悉都能回到真实订单、真实事件、真实操作人和真实时间。

### 不增加一线负担
系统尽可能使用已有数据自动判断，不为了分析再要求业务重复填表。

---

# 19. 建议施工模式

本轮建议采用 **逐 PR 验收**。

原因：

- 这轮同时包含 UI、分析口径、供应商批量导入、重新判责等不同风险面。
- 特别是 PR08 重新判责，必须在前面低风险 UI/分析改造稳定后单独验收。
- 避免再次出现一个大 PR 持续失败、反复跑 Gate 的情况。

每个 PR 的完成状态应严格区分：

`已修改 → 定向测试通过 → Gate通过 → Review通过（如需要） → 可合并 → 已部署 → 业务验收通过`

不得互相替代。

---

**施工基准原则：在任何 PR 中，一旦“美化分析区域”和“保护原工作区”发生冲突，优先保护原工作区。**

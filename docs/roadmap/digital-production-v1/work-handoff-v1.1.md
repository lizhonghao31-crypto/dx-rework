## 3. 从P01开工；ENV只在阶段验收前做必要cutover

不要再把Acceptance环境自动化作为P01前置。ENV-BASE已经完成，可直接开始P01。

P01—P04期间只维护现有旧Acceptance在线，不要求每个PR部署。P04完成后进入A1，才执行一次ENV-CUTOVER：

1. 如数据库在此前有新测试写入，再做一次切换前备份；
2. 用固定人工部署脚本把A1精确候选部署到`/opt/dx-rework-acceptance`；
3. 迁移独立`dx_rework_acceptance`；
4. 本机3202新API`ready/version`通过后，再一次性切Nginx前端alias；
5. `nginx -t`后graceful reload，不碰正式3201／生产数据库；
6. 停用旧root运行的Acceptance实例并撤销旧测试凭据；
7. 完成真实角色矩阵、业务流转、文件和截图，才判A1通过。

以后只在A2、A3、A4重复“固定候选部署＋阶段验收”，**不重做用户、数据库账号、HBA、目录、Secrets或Nginx架构**。

若部署自动化需要额外基础设施、runner或开放公网SSH，默认不做；除非业务负责人以后另行明确授权。当前优先级是业务施工，不再允许ENV成为时间黑洞。

## 4. 不能恢复的旧方案

- 不是工作日时钟：全部新流程连续自然时间；旧模块规则不全局改。
- 不是员工Excel导入：原表进系统，之后在线填写；完整内容和版式保留。
- 不忽略局部复版：仅改印花也记新轮；只重走影响部分。
- 不做同款分厂／分色先走：多PO同款同厂整款推进。
- 不让赵君签QC：物流沟通与现有质检分离，板房尾查另属样板。
- 不提前生产：预算制单可编，客户样板确认＋原老板审批＋技术条件后执行；不新增老板开裁审批。
- 不因代用号跳审批：编号可后补，但审批不可跳。
- 不让直接下单待提交开发单阶段超时：只记滞留。
- 不新增客户收样或出货：开发记录寄出日期快递号，大货复用原装箱作为本期终点。
- 不接考勤、不搞全岗位计件、不做综合评分。
- 本轮新通知只站内＋提示；旧订单原钉钉通知不全局停掉。
- 原“生产管理”原位改名“供应链总监”，这是正式唯一名称；不新建重叠角色，不重赋全员角色。

## 5. 代码与发布方式

从开工时最新main建立或接续已确认的`release/digital-production-v1`集成分支。每个业务目标用独立短分支／PR，进入集成分支；生产main仍可修现有缺陷，受控同步回集成分支。最终整包合入、测最终SHA、集中发布。

**Acceptance不逐PR部署。**每个PR完成代码、定向测试、Full Gate和必要Review后即可按计划合并；只在A1／A2／A3／A4四个业务阶段部署一次候选。阶段部署优先固定人工脚本，不再等待self-hosted runner或公网SSH自动化。

全部16组默认FULL。纯文案／独立CSS才可另按QUICK。每次Head二选一，不能同时消耗两套runner。多文件完整修改和定向测试后一次push；不要写一个文件push一次、再靠远端CI调试。

Codex默认只Review，每PR最多一次；不把“开始／继续”解释成委派Codex编码。已确认范围不自行加通用引擎、PLM、考勤或第三方平台。

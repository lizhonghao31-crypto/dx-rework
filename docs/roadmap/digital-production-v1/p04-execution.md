## 行为与边界

1. 数字任务作为原 TodoService 的可选提供方进入“我的待办”和徽标，不复制业务任务。即时按主办、有效代理、当前角色/在职状态及订单生命周期取数。缺失或失效主办成为管理人员的路由异常，不广播给全体工艺人员；上游角色无人时回退到有权限的总监/老板。
2. 0221 增加事件投影和提醒回执。源业务事件 + 接收人唯一；shown_at 与 acknowledged_at 均独立于任务、SLA、进度和待办徽标。前端每次只领取一条可见消息，服务端原子领取避免多标签/刷新重复；它是 at-most-once 展示领取，领取响应丢失时不会重复弹出，原待办仍保留。
3. 服务端独立扫描 P03 事件意图、当前期限修订及新订单已关联子单的原待办。不依赖打开页面，也不依赖 TODO_DELIVERY_ENABLED/TODO_TIMING_ENABLED。默认每 60 秒扫描，可通过 `DIGITAL_NOTIFICATION_INTERVAL_MS`（1 秒—1 小时）调整；启动/关闭与 API 生命周期一起管理，单实例不重叠，数据库锁防止多实例重复投影。
4. 当前节点临期/超时通知固定主办和计划规定的设计师、主跟单、技术主管、供应链总监范围；工艺/纸样完成知悉只发本单设计师。接受者和权限在投影及领取时再次校验。反馈正文、预算、成本、单价不进入通知 payload。后续 P05—P16 业务适配器继续使用固定任务/业务事件，不开放任意创建提醒或跨单选接收人的公共接口。
5. 同一事件可以给不同接收人投影；同一任务的新改派/期限修订是新事件。完成、取消、暂停、权限撤销、改派或被新期限替代的待办提醒在领取/刷新时失效。观察者只收到“查看”类消息，能执行者显示“去处理”；跳转真实任务页，最终办理仍由原业务接口核验。
6. 共享壳复用已有 60 秒待办刷新及页面恢复机制，不新增卡片定时器。PC 右下角；移动端放在顶部安全区域，编辑控件聚焦时不领取/不覆盖键盘与底部操作。确认只确认消息，队列继续领取下一条。
7. 新订单的来源子单按稳定 child linkage 判断 IN_APP_ONLY：TodoService 入队前检查，TodoDeliveryWorker 发送前再检查，覆盖同事务中先生成待办、后关联子单的顺序。原历史订单未被全局禁用。Acceptance 仍应关闭真实外部投递。

## 验证与交付纪律

- 数据库测试覆盖任务/计时原行为、跨标签领取、刷新不重复、确认不完成、改派、角色撤销、完成/暂停/取消后失效、服务器超时监测、权限与消息内容、主办缺失回退、子单事件去重。
- 全量真实 schema 的独立测试验证：旧订单 provider 调用保留；新订单入队前隔离及提交后发送兜底；原“我的待办”列表与徽标在确认提醒后保持。
- 6 种已排队投递动作（create/information/complete/reminder/escalation/update）验证新子单 provider 调用为零。
- 本地使用 PGlite 执行 SQL/API 测试与 221 个迁移回放；它的客户端串行化不能替代 Full Gate 的原生 PostgreSQL 并发证据。
- 按用户要求不做本地浏览器验收；多标签真实交互、移动端布局及阶段业务场景留在 A1 Acceptance。Gate、Review、合并、部署和业务验收分别记录，不互相替代。

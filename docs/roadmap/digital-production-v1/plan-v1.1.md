## 1. 目标、一期范围及明确不做

### 1.1 成功标准

主管能回答：这是什么订单、当前在哪个环节、谁负责、什么时候应完成、是否缺料或受阻、滞留了多久、应该到哪个原办理页面处理。数据沙盘能从汇总追到原单、节点、版本和时间证据。

业务人员的收益是：已有资料带入、不重复建外发单、不重复录实裁／实收／装箱，不为每次传递实物新增双人签收，不把主管变成全员记录员。

### 1.2 一期交付范围

| 范围 | 本期做到什么 |
|---|---|
| 订单源头 | 客户资料、直接下单、开发后确认下单、同款多颜色PO、代用号与正式号关联 |
| 板房 | 上衣／裤子在线开发单，面辅料，文员核配派工，纸样、裁板、工艺、车板、洗水、板房尾查、寄样 |
| 复版 | 所有实际修改都记录新轮次；只重走受影响工序，保留沿用关系、客户评语和问题原因 |
| 预算及制单 | 将原表内容与版式搬入系统填写，生成完整文件；接入原外发审批，完整六类制单页 |
| 大货产前 | 老板原审批后释放，纸样／唛架与预缩并行，条件汇合后自动开裁，内外裁接现有实裁 |
| 裁后与生产 | 整款工艺交接、现有QC检查、仓库整单发厂，接现有实时生产看板 |
| 回货与结案 | 接现有收货、质检、返工、工资、差异、装箱；本期装箱作为阶段终点 |
| 管理 | 已定稿座舱、板房主管管理入口、双进度条、站内待办、右下角提示、异常列表 |
| 分析 | 节点量、时效、等待、复版原因、数据质量、汇总到原单下钻 |
| 验收 | 真正独立Acceptance、精确版本发布、真实业务与权限接力、截图、兼容及回退演练 |

### 1.3 明确不做

不建设通用流程拖拽器、微服务拆分、第三方PLM部署、采购付款、完整库存、CAD／绘图编辑器、日常Excel导入识别、考勤排班、综合绩效评分、全岗位计件改革、快递接口、客户签收、报关或完整出货模块。

本期不做同款不同色分厂、不做部分颜色先走／先发厂、不把通用开发做成多客户销售分叉功能。不建设供应商账号。旧模块已有多次收货、旧单转厂等功能继续保留，不因上述新链路范围而删掉。

二维码仅为可选找单快捷入口：不强制采购设备、不逐件给大货贴码、不作为主流程运行前提。

## 3. 数据关系、客户档案及一处录入多处使用

### 3.1 业务对象与稳定关联

**工程方案：**保留现有`production_order_roots`作为已下单母单身份，开发来源使用独立来源ID。不要为每次编辑、每个PO、每次复版新建一张履约母单。

```text
开发来源（development_source_id）
 ├─ 开发轮次0：头版／开发板
 ├─ 复版1、复版2……（修改原因、受影响节点、沿用依据）
 └─ 客户确认下单 → 本次履约母单 production_order_id
                         ├─ 款色／PO明细1、2……
                         ├─ 预算版本 → 原外发选厂单 → 原合同与批准快照
                         ├─ 大货制单版本 → 产前任务 → 原实裁记录
                         └─ 工艺QC／发厂 → 原实时生产 → 原回货／返工／装箱

客户直接下单 → 先创建履约母单 → 待提交开发单（只记滞留）
                                  └─ 新开发来源及轮次关联回同一母单
```

客户确认下单幂等：重复点击、网络重试只能得到同一母单；开发记录不删除、不从历史中消失。进入生产座舱是管理范围变化，不是把数据从开发表搬走。

未下单开发不强制拥有履约母单；它的节点通过开发来源／轮次关联。现有0217只接受履约母单，因此在P03补关联能力，不能造一张虚假客户订单来满足外键。

### 3.2 母单与PO数据要求

| 层级 | 保存什么 | 不允许什么 |
|---|---|---|
| 开发来源 | 稳定ID、设计师、类型、设计款号／代用号、可选客户、原始资料 | 通过同款号字符串把不同来源自动并单 |
| 开发轮次 | 轮次号、来源、评语／问题、发布版本、路线、引用前轮 | 用旧轮次码悄悄操作当前轮次 |
| 履约母单 | 客户、产品分组、设计师、主跟单、交期、生命周期版本、来源及采用轮次 | 把代用号当数据库主键；同款分色分厂 |
| PO／款色明细 | 稳定行ID、PO可空、正式款号可后补、颜色、尺码数量 | 在缺PO时虚构号码；补号导致重复开裁／重复生产 |
| 外发与执行子单 | 现有源单ID＋显式母单关联＋行映射 | 按后四位、名称或创建日期猜关联 |

沿用现有外发款号／颜色／PO业务表达，但**客户PO号、设计款号、正式款号、代用号在数据上不能偷换为同一字段**。确实同值也分别保留语义。

资料未齐可保存草稿；向下游发布时仅要求该动作真实必需的颜色、数量、适用货期、负责人员和技术资料。正式PO／款号晚到不是已批准急单的额外阻断；不能靠“草稿可保存”允许缺数量或缺实际款式定义就生产。

同款不同颜色的历史日期若不一致，明细原值保留，整单监管不晚于其中最早的约定期限；不据此建设分批推进。新窗口不得为做统一卡片静默覆盖明细交期。

### 4.2 修改与复版

**一次发布给执行岗位的实际修改批次，建立一个新复版轮次。**仅改印花也计一轮；草稿自动保存、查看、重复请求、仅补正式号码不是一轮新制作。

客户发起：从历史点击复版，客户评语必填、图片可选，问题分类可多选。内部尾查发起：同样保留修改轮次，但必填内部问题说明，不要求伪造客户原话。记录来源：客户新增要求／未达原要求／内部发现；原评语与补充解释分开，不覆盖原文。

修改分类保留用户的面料、纸样、打板、车板、二次工艺；注明“打板＝尺寸／版型，车板＝做工”。不擅自把纸样和打板合并导致历史丢失。

默认只激活本轮受影响节点；未重做部分引用前轮结果。尾查退回直接到问题环节，修好仍经尾查。仅寄工艺布片的轮次不伪造车板和整件尾查完成；其适用路线按工艺修改和设计师确认收口。

### 4.3 大货准备与原外发审批

```text
客户确认下单／客户直接下单 → 同款母单＋多个PO／代用号
  ├─ 预算表提前编辑，设计师填写实际外发范围预算
  │    → 复用原外发节点：跟单发起／IE给价／供应链总监确认／老板审批／财务核对
  └─ 跟单大货制单提前编辑保存（是否预缩、完整六类页面）

允许释放大货任务 = 客户样板确认已满足 + 原外发老板审批通过 + 有效制单已提交
  ├─ 文员委派大货纸样师 → 纸样与唛架完成（48小时）
  └─ 需预缩 → 仓库整批预缩（36小时）；无需预缩保留明确判断

允许开裁 = 上述释放条件持续有效 + 有效纸样与唛架完成 +（预缩完成 或 无需预缩）
  → 自动进入开裁任务（整款全部PO，24小时），不新增老板开裁确认
```

大货纸样、唛架、预缩“完成”不新加强制附件。纸样与唛架可以同一任务中分别保存完成事实，只有两项均齐才能解锁；禁止用纸样单一完成代替两项完成。它们与预缩是并行分支，完成顺序不限定；同一事务条件汇合只创建一个开裁任务。

批准后缺正式PO／正式款号的急单可用稳定临时标识继续；打印唛等确实需要正式号码的资料明确标未补齐，不伪造号码。补号同步合同、制单和关联索引，但不重复发布任务、不重置时限。

原合同回签、转厂价格控制、调价说明、财务核对均保留。**财务核对不是大货执行的放行条件，合同回签监控不另加生产审批。**

### 4.4 内外裁与整款推进

原系统老板批准后创建的裁床订单“记录已生成”与“新流程可以执行开裁”要分开。新单可以有待条件满足的记录，但在前置齐备前不能办理，不提前计24小时。旧单维持原生成／办理逻辑。

实裁按原模块录入与上传裁床单；外裁由主跟单登记完成，保留供应厂和依据，原本不适用的内部工人动作不强塞给外厂。外裁时限是否采用同一24小时作为计划参数列出，未明确时只记滞留，不自行当作已确认SLA。

所有PO必须全部完成本节点才能推进整款。允许保存某颜色的录入草稿／局部事实，但不产生“该色先送工艺／先发厂”的业务动作。原实裁和士啤片单位不得混用；实绩量与客户订购量保留各自含义。

### 4.5 裁后、工艺QC与发厂

```text
整款开裁完成
 ├─ 无印绣花 → 仓库准备发厂
 └─ 有印绣花 → 印绣花跟单收发／协调 → 工艺完成回仓 → 本厂现有QC检查
                  ├─ 合格 → 仓库准备发厂
                  └─ 需处理 → QC登记问题及处理要求，赵君协调收发 → QC复查

全款满足条件 → 仓库一次确认实际发给同一个加工厂
             → 接现有实时生产看板 → 现有回货／质检／返工／装箱
```

QC最简表：关联母单／PO、检查人和登记时间自动带入、结果（合格／需处理）、问题说明、可选图片、处理结果与复查记录。**不把复杂片数核算作为本期前提**；只有业务原本已有、确有用途的检查数量才复用，不制造新“裁片库存”。QC结果未合格整款不向加工厂放行。

赵君不签署检查合格，不被系统自动指派“质检处理人”；供应商返修由其沟通收发，QC决定检查结论并记录复查。也不因为工艺检查不合格就自动创建现有返工扣款单。

新链路实际发厂才激活工厂生产监控；批准可以生成关联生产记录，但不能把“批准时间”冒充“实际发厂时间”。旧系统既有订单的监控起点不被回写。

船样：目标寄出日＝客户合同交付日减10个自然日。跟单负责大货船样协调及寄出事实，开发样衣仍由设计师记录。目标日期随获批合同交期变更保留新旧版本；没有合同交付日期就显示待补，不能用外发厂回货日期替代。

原制单“M码齐色各2件”等样例继续作为本单技术资料可填写，不自动成为所有客户统一数量。用户仅将提前10天、允许加裁5%、到料48小时固定化。

到料清点48小时必须从**工厂实际收到面辅料**起算，不从仓库发出、老板批准或系统建单起算。工程方案：主跟单代录工厂确认到料及清点结果，优先复用已有业务事实；未取得到厂事实时只列待确认，不能宣称已经开始可靠倒计时。不新建供应商登录或物流接口。

开发阶段终点只要求寄出日期、快递号，不监管客户收到。大货本期以现有装箱业务完成作为阶段完成证据；特殊短装／余量取消由供应链总监作特殊结案，保留原因、原订购与实际数量。仍存在的质量／差异事项不得被自动标成已解决；在结案界面显式展示，由总监决定例外。财务核对、工资已发放不是新增完结条件。

**“本期已完成”不等于货物实际出柜或客户签收。**这些暂不建设的事实保持未知。

## 5. 交接、等待、补录及时间可信度

本节是针对已认可方向的**工程实施方案**：不引入每次双签、不把主管变成代录员、不把登记时间伪装成准确净工时。

### 5.1 正常操作最少化

| 场景 | 操作 | 自动发生 |
|---|---|---|
| 本工序结束并交出 | 本岗位一次“完成并交出” | 记录完成／交出，查找已指定下游、检验条件、创建或激活任务、生成站内事件 |
| 设计师检查工艺通过并交文员 | 一次“确认并交出” | 保存设计确认；不要求先点已收到，不触发工资 |
| 纯文员递件 | 文员一次登记转交，或下游一次接收补同一条交接 | 不再建立两个强制签收任务；不重复计生产完成进度 |
| 已知辅料未到 | 不额外报异常 | 由物料状态自动显示等待项及设计师责任，不重复填写缺料单 |
| 未收到／资料不符 | 接收方仅在异常时反馈 | 关联交出人，生成待核实事项，保留原事实；不自动判罚 |
| 上游漏记、下游已收到 | 下游“已收到，补交接” | 保存下游收到事实，提示上游补记；不伪造上游准确完工时刻 |

扫码只定位任务，办理仍经过同一权限和前置条件检查。没有扫码设备也能从待办办理。

### 5.2 必须区分的三类状态

- **未来／未具备条件：**有预派信息，但没有办理SLA。等待本身可统计，物料可提前预警。
- **可办理但尚未开始：**任务已经到本岗位且条件具备，SLA开始；不允许靠不点“开始”延期。
- **办理后受阻：**原SLA保留，追加阻断区间、原因、当前处理人；不清空原时间。

核配主料不齐时，文员仍需要在4小时内完成“核配通过或说明缺项退回”这一动作；纸样不能启动。补齐后默认只复核缺项，除非资料其他部分也有变化。原核配历史及期限不清零；本次复核额外响应时限未配置时只统计停留，不能自动再赠4小时。

交接“未收到”没有自动过期视为签收的规则。异常反馈及时性可留事实，但沉默不能成为签收证明。存在争议的等待归属标待核实，技术主管处理例外；不自动扣工资。

### 5.3 时间事实模型

| 字段／含义 | 规则 |
|---|---|
| `recorded_at` 系统登记时间 | 服务端生成，不接受客户端覆盖 |
| `occurred_at` 实际发生时间 | 正常现场操作默认当前；补记可填写过去真实时间；不知道时允许为空 |
| 时间来源 | 现场本人、本人补记、接收人补交接、主管核实更正 |
| 时间质量 | 现场登记／补报未核实／已核实／缺失；不是“系统保证实际动作精准到秒” |
| 更正 | 原记录不覆盖，追加更正事件和原因，引用被更正记录，重新计算有效视图 |
| 幂等 | 同一业务动作ID重试结果相同，不重复完成、发待办、开复版、记工资 |

例如10:00确实交出、12:00补记，核实后下游4小时SLA应截至14:00，不应截至16:00；系统仍保留12:00登记和更正依据。若10:00只是估计，显示待核实，不拿它作精准个人耗时排名。

接收人补交接可让符合全部硬条件的任务继续，但不能跳过客户确认、老板审批、关键物料或QC。上游真实完成时间未知时保留未知，不能把下游收到时间批量填到上游所有工序。

### 5.4 与已有0217不可变时钟的兼容方式

已经合并的0217要求`warning_at`、`due_at`非空，且只允许一次写`completed_at`。不直接改旧SQL文件、不取消历史保护、不先造一个假期限。

**P03的方案：**

1. 任务实例与时间事实始终可以存在；SLA是可选关联。无时限任务不创建强制带期限的时钟行。
2. 开发来源任务也要有稳定任务身份，不必先造履约母单；新增任务通用关联，已有订单时钟通过显式关联复用。
3. 原时钟保存首次基线；核实补录引起的时间订正、以及“工序时效设定”对未完成任务的策略覆盖，都通过**追加期限修订记录**形成当前有效期限，保留原值。不得直接UPDATE 0217不可变行，也不得因改派、刷新、驳回改变首次进入事实。
4. 前端显示当前有效期限及必要的“已更正／参数已调整”标识，历史页能看原期限、当前有效期限及修改人／修改时间，不堆砌常驻说明。
5. 重复完成请求由业务服务识别既有动作并返回原结果，不能每次触发不可变触发器后报500。
6. 取消、暂停、复版、返修各有真实事件，不用删除时钟来清理状态。新复版创建新任务实例，不修改前轮实例。

这不是建设通用事件溯源平台；只记录本期确有用处的任务、版本、交接、阻断、更正及通知事件。

### 5.5 不可夸大的数据能力

交接记录得到的是办理周期或等待周期，不是净加工工时。没有设备或人工信号的时间段保持未知。合并纯中转后只统计整段中转等待，不伪称精确分出了每名中转人耗时。

## 6. 时限、双进度及预警规则

### 6.1 已确定的自然时间SLA

统一服务器保存UTC时间戳，业务日期及显示按`Asia/Shanghai`。一小时＝3600秒，一天＝24小时；旧模块的剔除周日算法保持原样，不全局替换。复用旧领域时如存在与新自然时间规则不一致的计时，在新版来源适配层分流；不得以复用为由让新版SLA继续扣周日，也不得回写旧单期限。

| 节点 | 时限 | 起点 | 完成条件 |
|---|---:|---|---|
| 开发文员核配 | 4小时 | 开发单正式提交，文员任务可办理 | 核配通过，或登记缺项退回；三岗位预派不是核配通过前置 |
| 开发纸样 | 48小时 | 前置核配具备、文员已派工并交付 | 完成纸样；有印绣花时工艺开发板上传满足 |
| 开发裁板 | 4小时 | 纸样已完成交出且裁板主办已指派，裁板可办理 | 本轮裁板完成交出 |
| 开发印花 | 4天／96小时 | 设计师实际发工艺且条件齐备 | 印花完成交回 |
| 开发绣花 | 4天／96小时 | 同上 | 绣花完成交回 |
| 开发印绣花组合 | 7天／168小时 | 本轮组合工艺开始 | 组合工艺完整交回；不把两个4天相加 |
| 开发洗水（内／外） | 1天／24小时 | 文员登记实际送洗 | 文员登记洗水收回 |
| 开发车板 | **24小时** | 工艺确认完成并由文员交到车板；无工艺时按前置完成后的实际可办理时间 | 本轮车板完成并交出 |
| 板房尾查 | **4小时** | 车板完成，且需洗水时洗水已收回；每次返修后重新进入尾查均单独计时 | 尾查通过，或明确退回问题节点 |
| 大货纸样与唛架 | 48小时 | 批准后任务释放、文员派交 | 两项均完成；无新增强制附件 |
| 仓库整批预缩 | 36小时 | 批准后有效制单要求预缩、实际可办理 | 仓库提交完成 |
| 本厂整款开裁 | 24小时 | 审批及纸样／唛架／预缩前置全部满足 | 母单全部PO开裁完成 |
| 面辅料到厂清点 | 48小时 | 有依据的加工厂到料时间 | 主跟单代录清点确认／问题结果 |
| 船样寄出 | 客户合同交付日前10自然日 | 已有有效合同交付日期 | 寄出日期＋快递号 |

时限从真正可办理事件启动，预先创建未来任务或文员预先指定三位师傅不触发三个倒计时。

### 6.2 尚未定的节点：先运行、只记滞留

当前明确**暂不设置SLA**的节点包括：中转、开发寄样、预算编制、制单编制、大货质检、仓库发出。设计师确认／文员转交、补料复核、大货二次工艺、外裁具体SLA、内部返修响应等尚未确认的节点，也按同一原则先运行。

支持`无时限`这一真实模式，不用空字符串、0小时或很大的假时限。UI显示“未设时限／已停留×小时”，不标按期／超时，不计入按期完成率分母；被缺料、质检问题实际阻断仍显示阻断，不等于一律绿色。

### 6.3 工序时效设定（第一版）

在**生产管理座舱**新增一个轻量入口“工序时效设定”，使用现有定稿视觉体系的小窗口／弹层，不另建复杂配置模块。该入口用于运行期调整业务节点SLA，不需要以后每次改“24小时→18小时”都开PR。

**编辑权限：**root、老板、供应链总监。其他角色不获得修改能力；页面可按权限决定只读或隐藏入口。修改时不扩大预算、工资或其它敏感资料权限。

**第一版覆盖规则：**

1. 调整某节点SLA后，**立即覆盖该节点全部未完成任务**，并对之后新进入该节点的任务生效；已经完成的历史任务不重算。
2. 重新计算基于每张未完成任务原有的有效`entered_at／occurred_at`起点，不把参数修改时间当作新的任务起点。
3. 例如车板从24小时改成12小时，已进行中的车板任务按“原进入时间＋12小时”得到新的有效期限；因此某些在途任务可能立即进入临期或超时，这是第一版有意采用的管理效果。
4. 从“无SLA”改成有SLA时，所有未完成该节点任务按原可办理进入时间生成当前有效期限；从有SLA改成“无SLA”时，未完成任务立即转为只记滞留，不再产生该节点按期／超时评价。
5. 临期阈值与SLA同属可配置管理参数。默认80%仅为初始值；调整后同样覆盖未完成任务的当前预警边界。
6. 每次修改记录：节点、修改前值、修改后值、修改人、修改时间；可选备注，但不把填写说明设为每次调整的强制负担。
7. 为兼容0217不可变时钟，不直接更新原`warning_at/due_at`。P03通过追加**策略版本／期限修订事件**生成“当前有效期限”投影，同时保留首次基线和每次覆盖记录。
8. UI应同时显示当前参数和最近修改信息；历史任务的原始基线及已完成结果保持可追溯。

这套规则第一版优先满足快速管理调度；未来如需要“只对新任务生效”“指定订单例外”等更细策略，再通过配置能力增量扩展，不作为本期前置。

### 6.4 节点提醒与物料提醒

**工程建议初始参数：**已用时限比例80%进入临期，达到期限而未完成进入到期／超时提示。80%是本计划的可配置初始值，不是问卷中的行业标准；不写死在UI或每个节点代码里。

```text
节点时间消耗 = (当前时间 - 有效进入时间) / (有效完成期限 - 有效进入时间)
临期 = 未完成且已达到该节点预警边界但未过期限
超时 = 未完成且到达／超过期限；显示真实超过量
完成结果 = 按实际完成时间与有效期限判断，不随当前日期继续变红
```

4小时任务80%时剩48分钟，48小时任务80%时剩9小时36分；不把“24小时内临期”作为所有任务统一规则。UI原演示文案必须跟真实口径一致，仅替换该业务标签，不改版。

物料使用日期型规则：D-1提醒、D日应到提醒、D日结束仍未确认到货则逾期，统一东八区日界线。新建时已经逾期，仅产生当前仍有效提示，不补弹所有历史阶段。日期修改保存历史；原已产生的迟到事实不删除。实际满足本轮所需量才可确认齐备，部分到货不足不能解除关键阻断。

暂停：保留原计划时间，单列暂停原因／人／区间，暂停期间不重复催做操作，但主管可见原计划偏差；恢复不重置原期限。取消：停止未来无意义催办，保留已发生任务及金额事实，不再生成后续生产动作。取消不是删除订单。

### 6.5 时间进度条

按“明确起点到明确目标的时间消耗”计算，而不是按页面加载时间。

**工程口径建议，随本计划确认：**
- 开发轮次：本轮开发正式提交→本轮有依据的目标寄出日期；没有目标日期只显示经过时间，不推算一个承诺。
- 已下单母单的大货阶段：客户下单的业务发生记录→客户合同交付日期。直接下单但尚未提交开发单的等待状态按R06只显示滞留，不对该节点作时效评分；进入后仍能看到原接单滞留，不清零。
- 加工厂回货期、预计发裁片日、客户合同交付期分别保存、标注；不得用其中一个替代另一个。
- UI明确当前是开发轮次还是大货阶段，不混用开发开始和大货目标。

有有效起终点时：`raw_time_progress = 100 × elapsed / duration`；负值按未开始处理；目标不晚于起点则提示日期配置错误，不输出NaN或强行100%。条形显示截断在0—100%，文字另显超期时长。阶段实际完成后冻结时间条，不再跟当前时间增长。

### 6.6 生产进度条

```text
生产进度 = 已完成的适用业务节点数 / 本阶段适用业务节点总数 × 100%
```

路线版本在发布时保存，明确哪些是业务节点、哪些只是任务／交接记录。通知、已读、预派人、纯递件、仅资料补号不进入分母。无时限但实际需要完成的业务节点仍进入分母。无需工艺／无需洗水的节点不进入分母。

并行的纸样／唛架组合与预缩必须按固定口径计数，不因一个组合拆成两张技术表就额外增加进度。具体节点清单与流程模板一同写入测试快照。

复版的新轮次有自己的进度；未重做节点以引用沿用表示，不把一次沿用当本轮重新完成。原轮次历史不清零。部分PO保存完成事实不等于整款节点完成。

两条比例可以对比，但差值不等于精确延期天数。节点时限＋真实阻断决定提醒；不通过平均节点权重、考勤或样板假数据产生“预计晚1天”等无依据结论。参数未齐时不得上线伪精确预测。

### 6.7 预警与办理分离

任务解决、物料齐套、QC复查通过等事实解除当前风险；“我知道了”、刷新、改派不解除。风险持续出现在主管列表，显示原因、责任处理人、目标时间和原办理入口。不同事件（临期／到期／新反馈）可各通知一次，同一事件不循环刷屏。

## 7. 站内待办、右下角提示与接收范围

### 7.1 两层数据，不混成一个状态

- **办理任务：**谁需要完成什么、截止时间、完成／阻断状态。
- **提示事件：**谁需要知道什么、是否弹过／已知晓、应去哪个任务。

共用现有“我的待办”入口。知会类事项明确是知会，不伪装成可操作工序，也不影响生产完成比例。技术任务和告知事件区分计数，避免“知会也必须办完才流转”。

### 7.2 右下角小弹窗

沿用定稿UI颜色、字号、按钮，PC右下角不遮挡主提交区域；移动端用同风格安全位置，避开底部操作和输入法。提示只含当前用户有权知道的订单摘要、事件、期限，不带预算利润、私密附件地址。

- “我知道了”：关闭本事件提示，保存知晓；不完成任务、不改变SLA、不删除未完成红点。
- “去处理”：跳原办理页面，不自动提交，不跳到新造的重复表单。
- 同一人同一事件只弹一次，多事件合并／排队，刷新、多个标签页不反复轰炸。
- 已由他人完成的事件过期后不再弹可办理提示，打开旧链接显示真实只读结果。
- 页面关闭或系统后台挂起时不承诺OS推送；重新进入后补取未查看事件和未完成任务。
- 不强迫用户一直开网页才能在后台计算超时；服务器监控持续执行，浏览器仅展示。

**技术方案优先复用既有拉取机制。**确无现成通道时采用单个增量拉取接口、游标和可配置刷新间隔，不为每张卡片建立定时器，不先引入消息中间件。多标签去重仅影响提示展示，不影响业务事实。

### 7.3 本期通知矩阵

## 9. 表单原件迁移与计算验收

### 9.1 总原则

固定模板线上填写，不做自由排版器；原有信息一项不丢。屏幕编辑可用合适输入控件，打印／导出按原件版式组织。动态明细可续页，重复表头、页码、图片说明和末页总计不能丢。

同一字段系统已有则带入，只补差异。存储结构化字段＋附件ID＋版本；不能只有一个PDF文件冒充可填写表单，也不能只实现主单前几项字段。

### 9.2 两份开发单完整清单

共同保留：客户、款号、数量、尺码、设计师、下单日期、中央设计图及说明、主布A／配布B／配布C、布行、品名、幅宽、克重、成分、用量、辅料；右侧原有朴料、门筒朴、车缝线、钮门线、针距、洗水整烫、包装方法、尺码标识、主唛／主唛车法、码唛／洗水唛／标记、下单与回版日期等。

- 上衣尺寸：衫长、胸围、腰围、脚围、袖长、袖口、夹圈、袖肥、领阔、前领深、领高等原行。
- 裤子尺寸：腰围、不同量法坐围、脾围、脚口、前浪、后浪、裤长等原行。
- 尺码列、测量行可增减；套装按照原答用上衣／裤子两份开发单，可显式关联，不硬塞一张表。
- 单位允许选择英寸／厘米；英寸分数保留原表达和精度，不自行转换导致数值差异。
- 原样例“初版／复版／齐色版”不作为新的三种开发类型恢复；按用户最终的头版／开发板＋轮次表达替换这一已明确变化区域。
- 上传图片已带箭头和说明，不建设画图；可上传局部细节。菲林可选；专有文件允许私有保存，不承诺浏览器在线编辑。

### 9.3 六页制单内容对应

| 原件区域 | 必须可填写／生成的内容 |
|---|---|
| 第1页生产主单 | 品牌简称、设计款号、款名、类型、年份季节、下单总数、交货期、面料类型／成分、制单日期、备注、加工工序、跟单、纸样师、款图、多个PO／颜色内外文／尺码数量矩阵、合计、船样、加裁、车缝要求、评语、打印人日期页码 |
| 第2页面料单 | 原共有抬头信息、面料小样仅供颜色参考说明、物料名称、使用部位、不同成衣色对应物料色、备注 |
| 第3—4页辅料单 | 车缝／包装物料分组、成衣颜色、物料颜色、辅料名、类型、部位、规格、单件用量、备注；按实际行数续页；到料48小时清点条款 |
| 第5页工艺单 | 主唛、腰卡、吊牌、洗水唛、二维码唛等图片及对应车法／位置说明，包装辅料图片文字，不把图当可省略装饰 |
| 第6页尺寸表 | 量法、测量部位、正负公差、单位、可变尺码列、英寸分数，原共有抬头信息 |

对原件仅有明确授权的固定文字变化：公司抬头换成“广州市达兴制衣有限公司”；船样期限动作按最新“寄出”而非样例“回厂”；开发类型按最新两类。其他文字不要自行润色或纠正。

车缝基本要求按原件／用户截图四条原文逐字存为模板，本单由跟单按客户要求修改，历史版本不跟着新模板变。原件中可能不常见的用词也不擅改。原表样例日期之间的不合理先后不得照作新单默认。

### 9.4 预算表字段、公式与精度

原件可见表“预算表 (2)”A1:J55，隐藏Sheet1为候选字典而非全部业务节点。标题公司主体按用户最新决定；产品性别、面料属性、产品类别、设计师、月份系列、设计款号、多款号／数量、图片、业务跟单、日期均保留。

主料、辅料、外发工序明细列：类型／物料或工序／规格／单位／供应方／单件用量／不含税单价／金额，保留运费、CM、成本、销售单价、利润。

```text
明细金额 = 单件用量 × 不含税单价
主料合计 = SUM(原J9:J15对应的主料行)
辅料合计 = SUM(原J18:J42对应的辅料行)
外发工序合计 = SUM(原J45:J48对应的工序行)
成本合计J52 = 主料合计J16 + 辅料合计J43 + 工序合计J49 + 运费J50 + CM J51
利润J54 = 销售单价J53 - 成本合计J52
```

J51是CM，J52是总成本，J53是销售单价，J54是利润；它们不能替代IE价或外发实际加工预算。设计师填写本次实际外发范围预算，系统直接向原外发发起资料带入，不擅自拆减全包CM。

本次原XML核对样例：主料26.88、辅料5.719、工序3.2、运费0.3、CM8.3，成本44.399；销售48，利润3.601。**只作验算样本，不是新单默认价格。**源表共享公式必须展开正确，不能当成手填常量。

计算复用现有精确金额工具，禁止JavaScript浮点累加直接作财务值。保留中间用量及金额必要精度，最终展示按平台金额2位、IE最多3位等已有效规范；不先把5.719舍入成5.72再累加后宣称与原表一致。输出44.40／3.60与内部44.399／3.601分别验证。

“厂供”只是供应方式，不自动创建同名供应商；预算提交不等于物料已经采购、到货或批准使用。合思去留、付款和采购控制本期不改。

### 9.5 版本与附件要求

表单草稿自动保存与正式发布分开；流转引用具体发布版本。关键资料更新后，旧版本已完成的纸样／唛架等不能悄悄替新版放行。开裁前跟单发布变更并通知指定三方；日期变更需总监批准。

开裁后本期不提供制单实质变更入口，但编号补齐保持允许。既有外发转厂／价格例外未获授权删除，仍按原有控制且全款一致，不能用制单编辑绕过。

附件复用已有上传、类型大小限制、私有存储和访问控制。没有安全预览能力的专有资料只支持授权下载；不强求所有菲林/CAD文件可在线预览。对外技术单生成链不得访问或夹带预算利润材料。

## 11. 实施组织、分支与PR拆分原则

### 11.1 采用“一个环境工作包＋16个业务PR＋最终发布验收”

计划编号P01—P16不是GitHub真实PR编号；创建时才填实际编号。每PR围绕一个可独立验收目标，包含自身schema、接口、权限、页面、待办、必要测试和文档，不另拆“补权限／补通知”作为补锅PR。

状态机、权限、金额、数量、迁移、跨模块、共享提示和发布均FULL。本计划16组均触及至少一项高风险边界，因此默认FULL；后续独立纯CSS／文案维护才可QUICK。每个Head只跑对应Gate，不能为本计划另建平行Full／Quick套娃。

P07、P09、P10属于较重但边界清晰的业务闭环。若实际变更超出一次可审核范围，只允许在开工前按可验收业务子目标拆分并记录，不先开巨型PR再陷入反复失败。

### 11.2 分支与发布策略（工程方案）

- ENV-BASE已经完成，可从当时最新`main`建立或接续`release/digital-production-v1`集成分支。
- 每个P编号用独立短分支，PR进入该集成分支；**不逐PR部署Acceptance**，仅在A1—A4四个阶段边界部署候选，不直接替换生产。
- 原系统生产缺陷继续在main修复。定期受控合入集成分支并重跑受影响测试；最后禁止直接以旧集成分支覆盖main上的生产修复。
- 开工前验证现有CI对非main目标PR是否有效，风险识别按真实base/head。若现有硬限制不支持，先在ENV工作包处理，不能跳过Gate。
- 最终发布PR将完整候选合入main，锁定最终合并SHA。对最终合并SHA执行验证并构建发布包，Acceptance验收同一候选产物，生产部署同一包；不能拿合并前截图代表不同合并结果。
- 新建入口有显式开关；已创建新版订单的办理开关与新建开关分开。关闭新建不等于把在途新版订单改回旧版。

分支名称和开关名称为技术建议，实际同名分支存在时先检查归属，不覆盖他人分支。此策略不包含本轮自动创建分支授权。

### 11.3 每PR固定交付要求

开工只做一次：读相应源文件、确认base/head、确定允许改动文件和禁止项、选择Gate、列验收场景。先本地完整组装和定向测试，再一次push。任何相关失败先读真实日志，不重复跑未改的确定性错误。

必要Review只在最终代码稳定且Gate已绿后进行，每PR最多一次，finding由当前Work核实修复。Gate变更后旧Head证据失效。

报告分别列：代码完成、定向测试、Gate、Review、合并、Acceptance部署、业务验收；不把这些状态合并成一个“通过”。

### 13.3 不触碰真实订单的测试与清理

测试数据生成器使用`test_run_id`、明确TEST前缀、独立测试身份和记录归属清单。清理只作用于该清单及其明确依赖；不能按日期、客户简称、某个测试前缀模糊LIKE删除所有记录。

`production_order_roots`不可删除是现有事实。实验库需要重置时可在**已证实独立、专用于该轮的库／schema**整体恢复合成基线；不能为方便测试在生产中关闭不可变触发器或TRUNCATE共用表。

清理前后做非测试记录校验，保留测试报告；只输出经过脱敏的日志和截图，凭据输入框、session、临时签名URL不得出现在报告中。

## 14. 正式发布、迁移和回退

### 14.1 迁移纪律

所有已合并迁移及其checksum视为不可变文件；新增结构必须新迁移，按实际最新manifest编号，不把本计划中的概念表名当现成表。新增表／索引／关联尽量增量，不批量改旧订单。

新旧隔离除了母单根记录，还要覆盖：API选择、子单来源、任务、通知、工资来源、报表口径、浏览器路由、执行权限。新单标记缺失时不能自动按“没有root就是旧单”放行；只对明确旧来源适用旧逻辑。

上线后旧单的新增返工／收货继承旧生命周期。翻单或重新承接的真正新履约显式建新版母单；引用历史技术资料只作为来源，不改变历史订单身份。旧开发的后续事项不会仅因记录创建日较新就自动切新版。

### 14.2 最终集中上线REL-01

1. 合入main上的必要维护修复，冻结完整候选和数据库迁移清单。
2. 逐场景完成M0—M5以及关键旧业务回归。实际人员仅在测试身份／隔离库进行验收。
3. 对最终合并SHA执行Gate、构建和包校验，在Acceptance部署准备投产的同一候选包并验证。
4. 如果Acceptance使用路径前缀而生产使用根路径，不能拿不同Vite构建包冒充同一产物。应在测试环境提供生产等价路径验证生产候选包，或采用已验证的运行时配置；记录构建配置与包hash，不临时重构整个路由体系。
5. 保留数据库备份和已验证恢复记录，确认部署目标、通知配置、附件权限、版本标识。
6. 负责人明确批准后，在选定窗口集中部署；部署新旧兼容代码，不对旧订单切换生命周期。
7. 开启新版新建入口，执行小范围真实冒烟：登录／读取／新建授权检查、旧单读取办理、版本与监控；不自动创建或删除未授权生产测试单。
8. 留观期间按日志和已出现的真实问题修复，不借上线继续扩大范围或再改UI。

最终生产部署仍由负责人控制。本计划不代替生产密钥、安全组、数据库写入和发布的明确授权。

### 14.3 回退不能等于删库恢复到昨天

区分两种情况：

- **尚未产生新版业务：**可关闭新建开关，按已演练的兼容包／配置回退。即使只加了表，也要验证旧程序的schema-version检查不会拒绝新schema。
- **已经产生新版业务：**先停新建、保留既有新版订单读写或有控制地暂停它们，不能强制改回旧流程，也不能删掉其任务、工资、实收、附件。优先部署修复版本或已验证兼容回退版本。

既有应用做精确schema校验，**不承诺任意旧二进制可以直接接新库**。REL-01必须提前准备可运行的回退候选及配置，验证真实读写；不得为了使旧包启动而随意删迁移记录／修改schema版本号。数据库整库恢复只在明确事故方案及授权下进行，不能作为普通UI回退操作。

### 14.4 版本与证据最小集合

```text

构建：包hash、构建配置、依赖锁文件hash
数据库：迁移版本与checksum清单

UI：同SHA真实浏览器截图，PC1536×960及必要移动端
业务：主管验收结论和未解决事项（不能空白当通过）
发布：负责人授权、上线操作记录、回退候选和恢复证据
```

## 15. 数据沙盘一期口径与业务闭环

### 15.1 首批指标字典

| 指标 | 计算范围 | 不允许的误用 |
|---|---|---|
| 独立新开发款数 | 去重开发来源，按设计师／品牌／时间筛选 | 同款多人完成任务累加成多个公司新款 |
| 复版数 | 实际发布修改轮次，按客户新增／未达要求／内部发现分组 | 只统计整件重做，忽略只改印花；把草稿保存算复版 |
| 岗位任务量 | 本岗位有效任务实例，主办／代理／接续分别留归属 | 全算给最后点击的人，或平均摊给所有人 |
| 节点按期率 | 有SLA且有效完成时间可判定的完成任务；展示分子分母和规则版本 | 无SLA任务当按期、取消任务当完成、低数据覆盖率却直接排名 |
| 办理周期 | 该节点可办理至有效完成，注明时间来源和质量 | 当成净加工工时、考勤工时或直接扣款依据 |
| 等待周期 | 真实阻断区间、原因和当前处理部门；并行等待取区间并集计算总等待 | 把同时缺两种料的同一小时重复累加成两小时 |
| 原因分布 | 物料、交接、资料、QC、客户变化等有依据分类 | 将待核实争议自动定责 |
| 时间完整情况 | 有效起终点、现场登记／核实补记／缺失数量 | 用补造时间让图表看起来整齐 |
| 登记延迟 | 仅对发生时间可信记录计算登记减发生 | 对估计时间输出精准分钟差 |

一条指标的明细需要能显示：来源ID、轮次、任务、人员、起终点、时限版本、阻断、更正、统计是否纳入及原因。范围过滤在服务端应用，导出与界面相同。

### 15.2 真正的数据沙盘试点

先用合成真值数据验证计算，再在上线后的真实授权范围观察，不为了试点伪造业务历史。每次分析保存筛选范围和口径版本，附一段结论、拟调整动作和后续观察时间；无需新建复杂分析审批流。

一期至少演练：

- 缺料等待集中在哪类物料／哪一阶段，能否通过更早填写预计日期减少被动追问。
- 某岗位任务堆积是实际加工慢、上游集中交单，还是登记延迟；从原单核实后再调分配。

调整前后可以对比，但缺少可比样本时明确写不能证明因果，不制造“效率提升80%”指标。考勤和人员净工时本期不接，复杂仿真、AI自动排程、个人综合评分以后另立需求。

## 16. 工期、成本、风险与未定参数

负责人负责业务拍板、最终发布和验收；Work负责代码、测试、修复、证据和文档。设计、技术、仓库、跟单主管参与各自里程碑验收，不要求新增一支全职研发团队。

### A.3 投影与对账

列表、时间条、节点条、待办和沙盘可以使用派生查询／轻量投影，但原事件和领域记录仍为权威。至少提供单母单重建投影和查询对账能力；不提供无人审核的一键生产全库回填。

投影晚于原业务时明确显示更新时间，不能因此再次创建任务或重复发工资。后台重放只重建派生数据，不重复原业务副作用。

### A.4 三个容易误做的实现细节

**核配反馈不等于核配合格。**文员在4小时内给出缺项退回应答，可以记录“本次反馈已完成”，但纸样的核配通过条件仍不满足，生产节点进度也不能据此增加。补料后复核是新的办理事项，关联原核配和缺料历史；未配置复核响应SLA时不自动再给4小时。不要为容纳重开任务而修改旧时钟的进入时间／延后截止，亦不要把新任务当前进入时间与过去的原期限硬塞进不支持该组合的旧表。

**客户确认下单不等于客户确认样板。**两个事实分别保留；直接下单且样板未确认仍不得释放大货。采用的样板轮次明确关联，不能因为预算／老板批准就自动补写客户认可样板。工程方案是在设计师已有客户反馈处记录该轮“客户样板已确认”结果及操作者，不接客户签收或客户账号、不新增一套审批；仅寄出不自动变成已确认。P07/P08一并实现这一必要放行事实。

**特殊结案不等于所有节点做完。**可停止该单未来催办并冻结阶段统计，但未执行的节点、未达订购数量不能改成实际完成；进度保留真实比例并明确“特殊结案”，不强制凑100%。

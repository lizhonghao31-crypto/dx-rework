## 1. 已确认的 V1 业务边界

- 第一版只选择加工厂，但数据模型必须为未来印花、绣花、水洗等工艺分别选厂预留扩展口。
- 一张订单同一时点不会拆给两个加工厂生产。
- 允许发生最初发给 A 厂、生产过程中改发 B 厂的换厂事件；不得覆盖历史决定，必须保留变更前后、原因、发起人、核实/审批和通报事实。
- 第一版只记录一个最终选厂与报价决定，暂不建设多供应商候选、多轮报价或竞价能力。
- 第一版五节点主链固定为：跟单创建订单 → IE 提供价格 → 生产管理调整价格并选厂 → 老板最终批准或驳回 → 财务核对。
- 老板驳回后退回生产管理重新调整，不退回跟单或 IE；每次调整和审批均保留版本，不覆盖历史。
- 订单转厂在生产管理首次提交选厂决定后解锁，作为辅助流程而非第六主节点：跟单发起先由生产管理批准，生产管理发起按价格阈值处理；转厂单价不高于最新有效决定时直接生效，超过时必须由老板批准；老板发起无需审批直接生效；财务不得发起或审批。
- 核心核对字段为：供应商、单价、数量、总额。
- 创建询价前已有正式 ERP 订单。
- ERP 每日导入和订单投影上线前，由跟单依据正式订单人工录入订单号、款号和数量；ERP 订单号作为阶段性稳定标识，系统不宣称已完成 ERP 权威校验。
- 订单投影上线后，创建询价必须改为选择权威订单并读取稳定 ID、款号和数量，不再接受人工填写这些订单事实。
- 合同由线下业务自行处理，不再作为平台流程节点、状态、待办或财务核对前置条件；历史合同事实只读保留。
- 录入错误由跟单负责；该错误不会造成工厂付款损失。
- 财务发现供应商、单价、数量、总额或实际工厂与决定不一致时，必须通报生产主管和老板。
- 中途由 A 厂改为 B 厂属于上述差异场景之一，必须形成记录和核实闭环，不能只依赖人工覆盖修改。
- 供应商第一阶段由内部人员维护；暂不建设外部供应商账号。
- 一个供应商对应一个工厂和一个生产场地。

## 2. 产品与技术原则

- 现用 ERP 无 API，但可以稳定完整导出；平台采用每日人工上传、预览、校验、确认和审计的导入方式。
- 报价选厂先形成可见业务价值，再逐步建设供应商管理、内部供应商协同和辅助排产。
- 排产 V1 的主要规则、候选方案和人工确认防线已基本形成；后续迁移规则、求解器和测试，重建数据接入与页面，不直接复制旧 ERP 巨型 UI。
- UI 继续以现有返工系统和项目设计 token 为 Golden Source，只做增量注入。
- 员工、身份、角色和 capability 继续使用现有统一权限底座，不新建第二套权限系统。
- 桌面端先完成综合平台与报价选厂；移动端报价选厂单独排期，期间不得改变现有返工移动端行为。
- 平台导航采用一级业务分组和二级功能入口；“我的待办”和“订单看板”作为跨模块一级入口置顶。
- 权限管理只保留一个中性的“人员与权限”枢纽，各业务模块不再各自建设权限管理页面。

## 4. 当前施工顺序

1. 既有数据、询价、IE 报价、生产管理决定和老板终审作为已完成基础保留。
2. PR1 至 PR5 已合并；2026-08-29 按最新业务决定收口为五节点流程，并下线合同节点。
3. 五个 PR 必须按顺序从最新 `main` 施工、全绿、Review、合并后再进入下一项；PR2 至 PR5 每个最多触发一次 Codex Review，Review 后修复只重跑门禁。
4. 桌面端五个 PR 完成后，再单独进行移动端报价选厂适配。
5. 质量管理中心在报价选厂五个 PR 完成并稳定后另行规划，不混入本轮。

本路线发生变化时，应修改本文件或新增 ADR；不得只依赖聊天记录改变后续施工。

## 5. 2026-08-29 流程收口决定

- 报价选厂界面、状态推进和统一待办只展示五个节点：创建订单、IE 报价、调价选厂、老板审批、财务核对。
- 老板批准后直接进入财务核对；生产管理核实换厂通过后也直接返回财务核对。
- 不删除历史合同表、合同事件或时间线证据；旧 `pending_contract` 订单由版本化迁移追加审计事件后进入财务核对。
- 财务以当前已批准的选厂决定核对供应商、单价、数量和总额，不要求绑定合同记录。


## 6. 2026-08-31 验收整改路线

业务负责人验收后确认，按最新 `main` 依次交付以下五个独立 PR：

| 顺序 | PR | 交付内容 | 门禁 |
|---:|---|---|---|
| 1 | 移动端越界回滚 | 恢复返工既有移动端底栏与“更多”行为；报价选厂桌面六列样式不得泄漏到手机；不建设新的报价选厂移动端 | Full Gate |
| 2 | 全系统数字与金额展示治理 | 普通界面金额和业务数量使用千分位；整数不补零，小数最多两位；底层计算、存储和审计精度不变 | Full Gate + Codex Review |
| 3 | 报价选厂列表与 Root 逻辑删除 | 列表按返工卡片顺序展示进度与字段；Root 可逻辑删除测试或真实订单，关闭待办但保留全部审计事实 | Full Gate + Codex Review |
| 4 | 财务核对与待办路由纠正 | 财务直接核对批准决定；一致归档，差异交生产管理核实；Root 超级权限不再自动产生非明确角色待办 | Full Gate + Codex Review |
| 5 | PC 表单与审批完善 | 工艺改为有序多项清单；完善老板审批摘要；修正桌面侧栏文字对比度 | Full Gate + Codex Review |

本轮继续遵守以下边界：

- 报价选厂只保留五个业务节点，不重新引入合同节点。
- 返工页面、交互和移动端行为是 Golden Source；报价选厂仅做增量复用。
- 桌面端先完成；除 PR1 的回归止损外，不开展报价选厂移动端设计。
- Root 保留全流程查看和兜底办理能力；业务待办收件人按明确业务角色投递。
- Root 可对录入错误、作废等测试或真实订单执行逻辑删除；逻辑删除只从业务入口隐藏，订单、附件、历史决定和操作事件不得物理删除。

### 6.1 数字与金额展示口径

- 普通业务界面统一使用千分位；整数不补小数零，有小数时最多展示两位。
- 超过两位的小数仅在展示层按四舍五入处理；数据库、API、计算公式、表单提交值和审计原值保持现有精度。
- 明确标注为计算明细或审计原值的字段可通过显式精度参数展示更多位数。

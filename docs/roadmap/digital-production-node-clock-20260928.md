# 数字生产平台｜节点完成期限与预警时钟底座

## 已确认原则

1. 节点真正进入“可以办理”的时刻才启动时钟；提前指定人员或提前生成未来任务，不启动倒计时。
2. 节点原始完成期限一旦生成，不因为改派、补资料、刷新页面或异常处理而重置。
3. 复版、返修等真正的新一轮工作，使用新的节点 occurrence，不覆盖上一轮历史。
4. 节点风险和整单交付风险分开。节点时钟只表达正常、临期、超时、按期完成、超时完成，不自行推导“整单高风险”。
5. 当前问卷尚未确认工作日历、夜间/午休/周日/法定节假日以及各节点提前提醒阈值，因此本PR不实现任何具体的时长算法。

## 本PR数据契约

`production_order_node_clocks` 每个节点实例冻结：

- `entered_at`：真正进入可办理状态的时间；
- `warning_at`：本节点的临期提醒起点；
- `due_at`：本节点原始完成期限；
- `deadline_policy_key/version`：生成这两个时间的规则版本；
- `completed_at`：实际完成时间，只允许写入一次；
- `node_key + occurrence`：支持同一业务节点在复版/返修等新轮次再次进入。

## 为什么现在不做“48小时怎么加”

问卷第47题仍需确认工作时间口径。未来时限计算服务负责依据规则算出 warning_at / due_at，再调用本PR repository 创建时钟。
因此以后调整“周日是否剔除”“4小时按工作小时还是自然小时”等，只增加/修改策略，不需要重构节点历史表。

## 不做

- 不创建具体节点；
- 不写死4小时、24小时、36小时、48小时、4天、7天；
- 不发通知；
- 不修改现有Todo timing；
- 不计算整单交付风险；
- 不触碰历史旧订单。

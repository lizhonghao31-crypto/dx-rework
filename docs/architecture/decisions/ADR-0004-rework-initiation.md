# ADR-0004：品控返工发起、草稿与提交边界

- 状态：Accepted for PR-05
- 日期：2026-08-02
- 需求基线：`docs/requirements/startup-requirements-v1.2.md`
- 前置基线：PR-03 公共 Tools、PR-04 角色权限与版本化基础资料

## 决策

PR-05 只实现已确认的 QC/生产问题返工发起链路，不把待确认 S-01
中的“本厂扫码、协助3F扫码”等非 QC 日常杂事伪装成返工单。
S-01 保持未关闭，必须在 PR-05 业务验收和合并前由业务负责人选择。

返工草稿与正式单据共用稳定 `rework_order_id`。首次提交时才分配
`RW-YYYY-MMDD-序号`；撤回后保留原单号和首次提交时间，修改后再次
提交不会创建第二张返工单。

PR-05 只开放以下状态：

```text
draft -> pending_process_configuration
pending_process_configuration -> draft
draft | pending_process_configuration -> cancelled
```

其中：

- 品控可以保存不完整草稿；
- 提交时必须具备款号、订单跟单、加工厂、问题部位、问题描述和正整数数量；
- 订单号只在业务已知时填写，不增加无价值的必填工作；
- 一张单只保存一个 `style_no`，不提供多款号数组；
- 同款号存在其他未完结单时只提示，不自动合并；
- 只有稳定身份上同时具备 `quality_control` 角色和
  `rework:initiate` capability 的本人可以写入、查看或撤回自己的单据。

## 草稿可靠性与防重复

所有写接口要求显式 idempotency key。业务行、幂等记录、操作事件、
附件绑定和待办 outbox 在同一 PostgreSQL 事务内提交。

每次修改同时使用版本号进行乐观并发控制。相同 idempotency key 与相同
请求返回原结果；同 key 改变请求语义会被拒绝。服务端不会依赖按钮禁用
来保证不重复建单。

## 附件

QC 图片/PDF 继续复用 PR-03 的私有附件协议：

1. 服务端生成不可覆盖、精确大小和哈希约束的上传授权；
2. 客户端直传私有 OSS；
3. 服务端复核元数据与内容 SHA-256；
4. 只有状态为 `ready`、由当前品控本人上传且尚未绑定其他业务的附件，
   才能在同一事务绑定草稿；
5. 已提交或已取消单据保留附件归属，不能绕过撤回流程替换证据。

当前服务器仍遵守 PR-03 边界：没有注入正式 Aliyun OSS SDK 客户端时，
附件接口失败关闭，不使用公开 URL、不伪装已联通生产 OSS。真实 OSS
配置和部署验证留在既定上线工作包。

## 基础资料与未来 ERP

订单跟单选项只返回本组织内、在职且持有 `order_merchandiser` 角色的
人员；加工厂来自当前有效的版本化供应商名录，并保存稳定供应商 ID 与
所选版本。本厂使用显式 `own_factory`，不伪造供应商记录。

数据表预留 `source_system`、`external_id`、
`external_idempotency_key` 和 `erp_node_id`。PR-05 仅允许
`manual` 来源，不读取或写入 ERP；未来接入必须经过显式适配层。

## 权衡

### 优势

- 刷新页面可按稳定草稿 ID 恢复，网络重试不会重复建单；
- 提交、撤回、取消和附件变化均有稳定身份及前后状态；
- 单号、款号、跟单和加工厂采用独立稳定字段，后续节点无需复制模型；
- 数据库触发器阻止绕过受控状态机和审计上下文直接改写。

### 劣势与风险

- 提交后不能直接编辑，必须先撤回；这是保留正式资料可信度的必要限制；
- S-01 未确认前，系统不能宣称替代全部尾部杂事表；
- 本地环境没有 PostgreSQL 服务，真实迁移回放与并发证据必须由当前
  精确 Head 的 GitHub PostgreSQL 16 门禁提供；
- 正式 OSS SDK 尚未注入时，UI 能展示完整上传链路，但实际上传会明确
  失败关闭。

## 回滚

未部署时关闭 PR 即可。迁移 0006 一旦应用，不修改历史迁移；使用新的
前向迁移停用入口或修正结构。回滚不得删除已产生的返工单、审计事件、
附件或 outbox 记录。

# 板房整改 PR04：Root 逻辑删除与交付核验

## 实现范围

- 看板与详情提供 Root 专用“删除订单”，使用既有应用确认弹窗；普通角色不能调用接口或借前端标志获得权限。
- 打板、杂事各状态均支持逻辑删除。数据库重新核验 Root、订单版本、幂等键与审计事件，在同一事务写入删除标记、关闭节点和待办。订单、人员、执行段、资料和工资事实不物理删除。
- 删除订单从看板、详情、人员筛选、附件可见范围、待办列表/数量，以及统一工资查询、汇总、导出、待结清预览和结清选集排除。旧页面保存的工资 ID 不能绕过过滤。
- 已有工资快照和已结清标记保持不变；数据库触发器防止删除后新插入板房结清标记，并用订单锁与并发删除排序。

## 本地证据

- API、网页类型检查，定向 ESLint、迁移校验、凭证扫描及网页构建通过；34 项相关单元测试通过。
- PGlite 隔离数据定向删除功能和工资保护用例通过，覆盖打板/杂事 × 待分配/制作中/待确认/完成/取消，Root 允许、普通角色拒绝、版本冲突、重复请求、审计唯一、待办关闭、资料不可访问及历史工资/资料不变。
- 额外工资导出回归通过：删除后明细工作表仅保留表头；查询总额为零、待结清为空、陈旧选集不能结清、已有结清事实不变。
- 并发删除/结清用例使用两个真实 PostgreSQL 连接，通过 pg_stat_activity 确认结清 INSERT 已经被删除事务阻塞后，才允许删除提交；断言旧快照仍不能插入结清标记。本地单连接 PGlite 不能执行该锁等待证明，真实并发证据以本 PR 当前 Head Full Gate 为准。

## 部署交接范围

1. 由业务负责人最终部署。发布版本须包含本轮四个 PR，数据库按现有迁移机制顺序应用 0188 和 0189；同时更新 API 与网页，保持代码、数据库及版本号一致。无需在 ECS 重跑 Full Gate。
2. 在人员与权限中明确给实际板房人员授予“板房师傅”；迁移不会把尾部工人自动转为板房师傅，也不会更换已有人员编号。当前助手未修改任何真实人员授权。
3. 验收环境使用隔离测试订单覆盖：打板创建→派工→完成→交接、杂事创建→派工→工时→完成→确认，以及返工、换人、取消、历史资料和 Root 删除。按 1440、1280、768、390、360 宽度检查全流程。
4. 核验大手机图片、空 MIME/扩展名不符图片、JPG/PNG/WebP/PDF 的上传、缩略图、点击放大、打印；打开卡片不能自动加载原图，保留+新增资料合计不超过 20 份。
5. 真实网页视觉验收仍未完成：当前浏览器安全策略拒绝本地隔离预览，未绕过限制；只读线上当前页面不能证明修复后的全部节点。CI、代码核验与实际视觉验收分开记录。尚未部署、未修改生产订单或员工权限。

## 峰值预算约定

预算是有明确余量的估算与阶段复核，不是磁盘预留、配额或生产并发写入保证。`statvfs.f_bavail` 按每条实际路径解析的文件系统聚合，同一设备只计一次基础余量，可用量取该设备所有探针的较小值；丢失/非法指标拒绝。现存旧版本、历史备份及附件已占用空间不会被当作可释放额度。

初步源码 S 取已有源码实际文件/块开销的两倍且至少128MiB，解包前改用 exact Git tree 的 blob+文件块测量；完整对象库 G 取已知本地对象库两倍且至少2GiB，明确 partial clone 不能证明远端对象大小。依赖 D 以实际可读依赖体积×1.5、至少512MiB估算；候选锁与可用基线不同时至少2GiB。构建输出 O 以既有构建体积两倍、至少256MiB估算。

下载阶段同时计源码临时集、独立对象库、认证源码库 `.git` 所在卷的 fetch 元数据增量（至少1GiB或现有对象库两倍）、工具 staging、build 依赖/输出、npm cache/解压临时集、candidate、安装 API release 与独立前端 release（不删除旧代），并计后续备份与 DB/WAL/日志余量。后四个包/安装路径按确切目标 SHA 分别探测，前端即使单独挂载也不能漏计。之后只计尚未完成阶段的增量。备份预留2×本库大小+256MiB；数据文件每个独立卷2×本库大小+256MiB；WAL 卷按2×max(DB大小,max_wal_size)+1GiB；日志及应用日志另列。每个实际卷再留至少512MiB、最多2GiB的5%基础余量。公式和逐项字节、挂载设备、缺口写入证据；任何卷不足均在对应重操作前拒绝。

若实际候选/依赖或并发业务超出估算，后续阶段复核仍可能拒绝；不能把早期通过说成最终更新通过。尤其当前现场40GB盘的空余未知，本 PR 不假设足够，更不替用户自动清理备份。

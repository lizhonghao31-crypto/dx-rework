# 2026-09-15 PR02：实际超扣与财务特批

本轮只处理已实际发生的扣款。拟扣责任金额 P 不变，现有累计实扣 A 加本次流水 X 得到 A′。A′ < P 按原流程跟进，A′ = P 按原流程足额结案，A′ > P 必须填写原因并转财务总监特批。未发生的计划扣款不录入实际流水。

## 实现边界

- 既有扣款接口增加可选 `specialApprovalReason`。输入新金额后点击特批，也通过此接口在同一事务记录实际流水并申请；未输入新金额则保留原特批接口，按已保存实扣申请。
- 服务端重新计算金额、检查权限及版本。实扣事件、流水、附件绑定、特批事件、不可变金额快照、案件状态、唯一财务总监待办和 outbox 均在同一事务内；收件人不唯一或任何数据库步骤失败均回滚。钉钉调用仍由提交后的原投递 worker 执行。
- 0183 增量迁移保留原金额精度、负数及冲销引用规则。实扣超过拟扣的新增流水必须在事务提交时关联其自身未决特批；只放开前端或直接插入流水都不能绕过此约束。
- `remainingAmount` 仍为 P − A，超扣时为负数。批准后的结案结果为 `over_deducted`，页面及财务报表显示“超额扣款（已特批）”。不把多扣伪装成足额或部分扣款。
- 特批退回保留实际扣款与原申请，仅恢复跟进。重新提交不重复记账。取消确认或取消意见输入不提交审批。
- 补充正常足额结案对先前“特批退回”待办的收口，防止已经足额的案件仍残留处理待办。
- 原财务读取、各应付会计范围、财务总监专属审核、Root 特殊验收规则不变；已完成订单中的扣款跟进不会重开生产流程。

## 历史补待办

复用 `TodoBackfillService` 及现有 dry-run/apply 入口。仅选择当前有效批次、尚未审核且没有更新申请取代的真实 `pending_special_approval` 记录；已完成生产订单仍可补待办，已取消或删除订单不补。

每个候选在事务内重新锁定并核验案件，避免候选扫描后已经审批却补发通知。使用原申请事件、原类别、原案件深链及 `external-special:<caseId>:<requestId>` 去重键。已有待办不重新建单、不重新发消息、不改变决定。原 outbox 的可重试投递仍使用原绑定及 source key；永久拒绝、账号配置错误等需先核实原因，不能用重建申请掩盖。

## 验证及部署注意

业务链覆盖：已完成订单、历史实扣结转、超扣无原因拒绝、恰好足额不走特批、实扣与特批原子保存、数据库提交约束、财务总监收件人冲突、outbox 入队后故障回滚、幂等重放、过期版本、只读会计拒绝审批、退回保留事实、补待办 dry-run/apply/重复执行、并发审核只成功一次、超扣特批结案及财务读取。原部分扣款与零实扣特批后恢复足额流程同时验证。

页面确认测试覆盖取消、空原因、超长原因、精确金额、未保存的部分实扣和零差额特批拒绝。运行结果以 PR 当前提交的 Full Gate 为准；本地嵌入 PostgreSQL 验证不代替真实 PostgreSQL 并发门禁。

用户负责最终部署与真人验收。本轮没有读取或修改生产问题订单；没有确认现网总监账号唯一性、实际手机接收结果或永久失败的钉钉原因。部署后先只读核实实际记录与迁移状态，再对有效待处理申请运行现有补待办 dry-run；不得用真实订单制造扣款来测试通知。

0183 支持负差额和新的结案结果，发布后不能只退回到不认识这些数据的旧应用版本。需要回退时保留新增数据并以前向兼容修复为主，不删除流水、申请、决定或历史凭证。

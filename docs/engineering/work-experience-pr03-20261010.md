# PR03 板房岗位同页办理

板房管理台原来默认列出授权档案的所有任务，打开任务后还需再进入开发办理或原派工页面；七环节风险数字取自最多 20 条预览。本次把岗位范围作为服务端筛选，风险总计在分页前计算，并在选中任务下方直接挂载既有业务表单。

## 范围与基线

目标为 `release/digital-production-v1`；已继承 PR02 最终 Head `aa19648c32d3b94bdcd4e6d8e785b9e1627fa808` 和合并基线 `a58f455772b254bd654696c126e2796da6ab79cd`。FULL；岗位范围、任务导航与正式派工读模型需要一次 GitHub Codex Review。沿用已有实际任务、原业务 API、授权、幂等、数量与工资事实；无 migration、部署或真实数据操作。

## 实际行为

- 默认“我的任务”只包含本人有效任务，分页前筛选；师傅不能通过 URL 改 scope 取得全体范围。文员可选人员安排与全部进度，主管可选待分派与正式派工，Root 保留原能力。每个范围仍先经过 Journey 的原授权。
- 七环节 KPI 的临期/逾期从完整授权筛选结果计算；前 20 条风险预览不再用于总计，原任务与档案计数继续区分。
- 正式派工读取 `digital_development_pattern_links` 对应的未删除原单与当前轮次均为 `pending_assignment` 的真实事实，且仅主管/Root 可用。每个待派工原单以一个真实当前数字任务作为资料上下文，不把文员转交任务或数字任务状态改成主管派工。结果仅包含标识，不下发价格。
- 选择任务直接显示左侧本轮原图、制作说明、数量和打样尺码，右侧当前业务表单；历史页继续只读。图片沿用原附件权限。主管正式派工复用原组件及原 API，文员预派继续走开发 dispatch，不合并两种权限或工资归属。
- 主提交后显示刚提交的动作及服务端当前可见的后续任务/主办人；无可见下一任务则明示。主管确认分派提示车缝按实际前置条件启动。筛选与选中任务保留在 URL。
- 顶部按钮可左右滚动七栏，原横向滚动可用；下方详情没有固定高度滚动区，页面保持自然纵向阅读。

施工图片只作结构参考，不采用图片里的示例值或旧文案覆盖 MD 正文与业务来源。

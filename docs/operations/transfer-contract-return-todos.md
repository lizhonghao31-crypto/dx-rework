# 转厂合同待签回：核验与历史补偿

## 范围及业务决定

转厂正式生效并生成当前合同 PDF 后，向原合同通知规则允许的主跟单、第二跟单生成站内待办。待办展示款号、新加工厂与合同版本，直达当前合同回传区。需老板批准的转厂在批准前不产生新合同待签回。

下载不完成待办；当前版本成功回传才完成对应跟单任务。连续换厂取消旧版未完成任务，不记录虚假的旧版回签。当前版本尚未生成完成不得回传；上传途中换版返回 409，提示重新打开当前合同。新版链接打开时若已换版，页面说明当前展示版本。

本轮用户对额度问题的原文答复为：**“每个合同版本各限 2 个文件、20 MB，保留历史文件（推荐）”**。来源：本轮 `request_user_input_async`，调用 `call_720b5ec00e9b48ed9ae5c60ee9ad1658` 第 0 项的用户答复。额度按实际合同文档 ID 统计；不重绑或删除历史文件，不改首次回签时间及历史审计。旧请求/旧文件重试不会完成新版本待办。

不新增钉钉通知；原合同通知、审批、财务及既有上传权限不扩大。待办路由失败不会把已生成成功的 PDF 标为失败，记录 `sourcing.transfer_contract_todo.deferred` 审计，供明确补偿。

## 历史补偿接口（部署后由用户决定是否执行）

以下是应用 API 路径；沿用当前站点的 API 前缀和已登录 Root 会话。不得从本地直接连接生产数据库。无启动补偿、无 migration 回填；普通管理岗位不能执行这些接口。

1. `POST /todos/transfer-contract-reconciliation/preview`

   请求体：`{"caseIds":["实际外发单 UUID"],"limit":200}`。`caseIds` 可省略，此时盘点最多 `limit` 条；若 `truncated=true`，须按明确订单分批。只读返回当前已生成、转厂生效且尚未回签的合同，包含 `caseId`、`documentId`、版本、新工厂、两跟单 ID。候选中可包含已经存在待办的合同，补录会按版本及收件人去重；候选不保证收件人当前可路由，申请时仍执行原权限策略。

2. 核对候选订单和版本后，`POST /todos/transfer-contract-reconciliation/apply`。

   请求头：`Idempotency-Key: 本次唯一请求标识`。

   请求体：`{"selected":[{"caseId":"盘点返回的订单 UUID","documentId":"盘点返回的合同 UUID"}],"reason":"本次历史转厂待签回补录原因"}`。

   每批最多 100 个不重复订单。该操作锁订单后再次验证当前版本、生成状态和未回签事实；任一变化、权限/路由错误或写入失败，整批回滚。成功响应 `reconciled` 与 `reused`；相同 key、相同请求重放返回原结果。不同 key 重复补录也不新增同版本同收件人待办。`reconciled` 表示投影核对已执行，通知策略排除的成员不会收到待办。

3. 查看对应跟单“我的待办”及 `sourcing.transfer_contract_todo.reconcile` 审计。校验演员为实际 Root，合同版本符合盘点结果。无新增该任务的钉钉 delivery attempts。只读角色不应出现新待办，也不能上传；Root 原有业务能力保留。

补偿不修改审批、合同 PDF、签回文件、财务状态及历史记录。部署和真实业务操作未由本次施工执行。

## 隔离验收覆盖

- 转厂待批准期间无新任务；批准生效且 PDF ready 后才创建。
- 主/第二跟单同版本两任务；任意合法跟单回传后共同完成；Root 保持可上传。
- 未指派跟单、财务及只读成员拒绝上传；既有成员通知排除规则保留。
- 连续转厂取消旧待办，新版独立；下载只读；旧版本请求不能完成新版任务。
- 同合同版本累计数量/体积、并发最后一额度；新版本不占用旧版额度；历史文件及首次回签事实保留。
- 重复事件和重复请求去重；历史补偿只读盘点、Root HTTP 鉴权、版本过期拒绝、失败原子回滚和审计。
- 投影失败留审计但合同 PDF 仍 ready；新任务及其生命周期不进入钉钉队列。

未测边界：真实浏览器视觉、真实 OSS、真实钉钉、生产回填、真实岗位操作及线上性能。本地合成样本/自动化成功不等于线上业务验收通过。

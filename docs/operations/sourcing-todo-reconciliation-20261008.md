# 外发报价与调价选厂待办轮次修复

用户授权本次独立 main 修复。正式截图中 SE20554035 的外发详情已经 5/5，但总监待办仍待处理；其余所见订单没有详情或历史证据，本次不推断其状态，也没有登录正式库执行补偿。

报价版本与总监决定版本分别递增，退回重报后不能互作待办轮次。总监新待办使用实际 `management:transition:<sequence>:<recipient>` 身份；成功报价、总监决定在原事务中终结该节点的旧投影。角色、单价、审批、数量、合同和冻结历史迁移不改变。列表仍展示各待办代表的动作；已完成项退出待处理计数，历史标题保留。

## 默认只读盘点

已登录 Root 可调用 `POST /todos/sourcing-reconciliation/preview`。请求体为 `{ "caseIds": ["明确的外发单 UUID"], "limit": 200 }`；省略 caseIds 为最多 200 项的有限盘点，`truncated=true` 必须继续缩小范围核查。接口使用只读、可重复读事务，不更新待办，不写审计，也不发送钉钉通知。普通总监或伪造 Root 业务角色不能调用。

逐项输出 todoId、caseId、原始进入与办结序号/事件、业务事实事件、当前节点、证据哈希或跳过原因。只认可同一单、同一来源事件的进入轮次紧接着已有合法 IE 报价或总监决定，并且业务事实和办结审计一致。仅当前节点不同、退回、缺来源、路由不明、未知类别和未办结轮次均不足以关闭。后续重入节点的真实新待办保留。

## 另行授权后的明确补偿

本次只交付代码和测试，不执行真实补偿。部署不会自动补偿历史数据。实际执行需业务负责人确认盘点结果及执行授权。

确认后由 Root 调用 `POST /todos/sourcing-reconciliation/apply`，提供 `Idempotency-Key`、`selected: [{todoId,evidenceHash}]` 和不超过 300 字的 `reason`。不能传“全部关闭”或仅传单号。服务先按固定顺序锁原外发单与所选待办，重新核查每一项；任一证据变化、身份不明或新轮待办未办结则整个事务拒绝，零关闭。原业务事实保持不变。

成功补偿追加 `sourcing.todo.reconcile` 证据审计和原平台 `todo.complete` 审计，使用既有终态投递通路。原待办及历史不删除；阻塞接收人的路由异常使用原机制收口；钉钉提供方终态由原 worker 完成。相同键、相同请求重试不增加审计、待办版本或投递；换请求内容复用相同键会拒绝。

回退应用代码不会重新开启已合法办结的待办；需要调查时按 todoId、requestId、补偿证据和完成事件核对，不能回写业务审批或要求总监重做业务。

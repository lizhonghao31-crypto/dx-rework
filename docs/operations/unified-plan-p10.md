# P10 有界读取与提交反馈

本增量对应 B09 与已确认反馈共因，只接入批准计划列明的请求客户端及其原恢复宿主。不改业务 API、payload、HTTP 方法、业务状态/资格、金额数量、权限、待办或历史事实；没有自动重试写入，也不改任何 CSS、管理座舱布局或时间设置。

## 使用者看到的结果

读取失败明确原资料尚未确认，可重新读取；不会被说成提交失败、空资料或尚未创建。服务端已知中文业务原因继续展示，包括多个真实阻断；没有返回可用业务原因的 409 不再推断“版本/状态一定改变”。401/403/含糊404给权限内下一步，不泄露别单资料。

写入已发送后断网、中止、408、5xx或成功响应不能验证时，显示提交结果尚未确认，保留原输入/请求依据，让用户先核对原记录。已取得可信成功回执而仅后续 GET 失败时，继续明确已保存，只提供重读目录/负责范围；不把成功改成失败，也不再次新增。草稿、发布与实际办理沿原独立回执，不混为完成。

GET 取消继续是读取取消；能在 fetch 前证明写请求已取消时，复用原 SubmissionCancelled，未发送且不造成未知提交。fetch 发出后 POST AbortError 不再当撤销成功，保留未知；响应 body 读取时的 GET AbortError 也继续取消，不误报坏格式。

主资料新增/改名等真实回执成功后，目录刷新失败显示“已保存，最新目录暂未读取”及“仅重读目录”。工资详情始终只读，首次读取失败也能重新读取，无工资写入按钮。生产负责范围在未知时冻结原内容与 key，不能用编辑后的新内容替代；后续权限拒绝不能否定前一次未知提交。

## 实际增量与恢复协议

request-response-feedback 只提供受控 fetch、JSON/原 schema 解析、原204无内容回执，不安装全局拦截器、不生成 key、不内置写重试。每个客户端保留原 URL、headers、credentials、业务 parse 与原错误类/code/status。没有“把全部客户端改成同一平台”的前置工程。

DigitalRequestError 增加 resultUnknown，保留实际 HTTP status/code。200回执无效、408、网络、5xx及原幂等冲突/处理中属于未知。开发办理、原生换人和资料补正的原 catch 只改用该分类；原办理资格、事务、角色和状态守卫完全不改。这样避免实际 HTTP200 的坏回执被旧的“非5xx就是拒绝”分支误释放。Sourcing 仍用原 SubmissionAttempt/SubmissionRequestError，明确拒绝、原 frozen closure、已确认成功及恢复窗口保持。

保留可用中文业务原因；未翻译英文机器报错、JSON/Schema堆栈或SQL诊断不进入正文。既有英文图片类型不符原因映射为原已支持的中文别名，原图片归一化恢复仍识别，错误 code 不丢失，未放松服务端图片校验。

主资料只对实际版本化 CRUD/ensure/默认人员响应做有据的回执字段校验，导入 preview/rows 不套 CRUD 形状。原主资料的已有启停规则保留，未借此给共享辅料新增恢复启用；P06仍仅四操作五岗位。收货主登记核对回执身份、款号、数量和时间字段后才清输入；生产范围核对原 `{saved:true}` JSON，不能把任意HTTP200当确认。原返工移除人员沿真实204契约，不虚构JSON回执。

## 回归与失败记录

新增实际客户端与方法/回执/取消单测，原共享错误、读取复用、SubmissionAttempt、供应商导入和样衣图片单测一起回归。新实际页面浏览器在1440/390两宽共24组：主资料可信保存+失败重读、未知保留、403保留；工资只读重读；独立负责范围保存/未知/未知恢复再拒绝。旧返工移除实际页面另覆盖204后读失败关闭确认框/仅GET、坏成功响应沿原body/key及过期不重发，原主动移除JSON分支另验未知→沿原命令恢复；生产范围与移除均沿原SubmissionAttempt既有23小时恢复窗口拒绝过期重发，不另造业务期限。另实际本人阅读17项与共享目录10项浏览器回归。

原 digital-operation-feedback 浏览器没有按旧脚本直接算通过：旧问题登记标题和旧已保存回读失败文案已过时；P02补料已改为独立资料补正回执。夹具按实际legacy上下文和当前命令补齐，分别验证可信补正回执与失败GET，不再把它伪装成旧resubmit未知协议。最初三轮脚本失配保留。409明确初次拒绝后新命令可以有新key，不能要求它与未知恢复相同；另加真实未知回执场景，核对相同frozen body/key、用户新编辑未被冒充已保存、后续只读不产生第三次命令。对两原宿主分别重开，核对完成事实与仅一次业务计数。

页面新夹具起初缺本人响应标识头触发原壳安全刷新，另缺原壳CSS导致遮挡；补齐夹具而非关闭身份保护或修改产品CSS。第一轮常规回归4项旧默认文案断言失败，按批准的读取/拒绝语义更新，保留原类/状态/请求次数与未读缓存断言。开发未知回执分类在发布前的新增回归发现并修正，不留成假绿。

最终HEAD的常规、类型、lint、构建、secret、FULL及唯一Review在PR记录，只有这些完成才称代码交付就绪。未执行ECS、真实订单或外部存储/ERP，桌面真实缩放/触摸仍待现场；D08已由用户选B并在P04实现原文员主动接回；此处沿用其同原键恢复和独立事实保护，不借反馈治理绕过。

## 唯一Review三项补修

生产命令的原内容核对入口独立于当前业务阶段；完成回执未知后刷新到production_completed，仍可同key/原body核对complete，得到可信回执后才解锁ship。未知请求按本人/订单/工厂上下文保留，换单不把旧结果带进新单、返回仍能核对原命令；不按刷新状态猜测原写是否成功。真实PG补同key complete在当前已完成状态复用及唯一完成事实断言，异key仍拒绝。辅料POST408保持未知并冻结编辑与原body/key，先读原目录回执，不把408当明确失败。负责范围的读取错误单独保存，成功重读清除旧错误并更新“最新范围已读取”，不清除其它生产错误。三项均沿原权限/方法/幂等与恢复期限，无业务校验放宽。最终补修HEAD门禁与回归记录在PR评论，不发第二次Review。

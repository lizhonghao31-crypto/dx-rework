# 供应商维护与新增申请：本轮执行口径

状态：2026-09-12 业务负责人已确认。

- Root、老板、生产管理直接新增、修订、启停及批量维护正式供应商，不提交申请；兼有跟单角色时直接维护优先。
- 订单跟单、印绣花/洗水跟单仅提交申请，老板或生产管理任一人审批；Root 保留全部特殊能力。
- 所有正式创建入口共用数据库防重：规范化名称 + 类型，包含停用供应商。规范化为去除首尾空白、合并连续空白、忽略大小写。不整理历史重复资料，已有重复资料的非名称修改仍可执行。
- 申请提交、重提、审批均检查正式库及其他待审批申请；退回必须填写原因，申请人修改后生成新版本。
- 同事务完成审批、正式供应商创建、审计和待办关闭。审批使用申请快照，审批人不直接改申请内容。
- 申请人只看自己的申请和自己提交的敏感字段，不扩大印绣花/洗水跟单的全局合同/收款字段权限。
- 三个顺序 PR：正式维护权限与统一防重；申请审批后端与待办；页面及链路验收。不增加特性开关或配套发布机制。

下附原施工方案供追溯；以上确认内容覆盖原方案相冲突的表述。

| 角色 | 查看供应商目录 | 查看供应商详情 | 直接新增正式供应商 | 修改/启停正式资料 | 批量录入 | 提交新增供应商申请 | 审批新增申请 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Root | ✅ | ✅ 全部 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 老板 | ✅ | ✅ 全部 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 生产管理 | ✅ | ✅ 业务全部 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 订单跟单 | ✅ | ✅ 按既有字段权限 | ❌ | ❌ | ❌ | ✅ | ❌ |
| 印绣花/洗水跟单 | ✅ | ✅ 按既有字段权限 | ❌ | ❌ | ❌ | ✅ | ❌ |
| IE / 财务等现有只读角色 | 按现有规则 | 按现有规则 | ❌ | ❌ | ❌ | ❌ | ❌ |

## 1.2 核心规则

- Root、老板、生产管理可直接新增、修改、启停正式供应商资料。
- Root、老板、生产管理直接维护时，不需要再经过审批。
- 订单跟单、印绣花/洗水跟单不能直接写入正式供应商目录。
- 跟单类角色只能在“资料维护”中填写供应商资料并提交“新增供应商申请”。
- Root、老板、生产管理三者中任意一人审批通过即可，不串行、不三人会签。
- 审批通过后，系统在同一事务中正式创建供应商并绑定申请记录。
- 审批前的申请资料不能参与正式外发选厂、合同或其他正式供应商业务。
- 正式供应商仍只有现有一套 supplier catalog / profile，新增申请只是正式建档前的暂存与审批层。
- 不新建第二套供应商目录。

# 3. 申请状态机

本期保持简单，建议仅使用以下状态：

| 状态 | 含义 |
|---|---|
| `pending_approval` | 已提交，等待 Root / 老板 / 生产管理任一人审批 |
| `returned` | 已退回，原申请人可修改后重新提交 |
| `approved` | 已通过并已经生成正式供应商 |
| `superseded` | 历史申请版本，保留审计，不再作为当前版本 |

## 3.1 不做的状态

本期不建设：多级串行审批、三人会签、永久“拒绝关闭”、复杂撤回流、自定义审批流配置、BPM 工作流引擎。

# 9. 印绣花跟单敏感字段边界

本轮必须明确：**“可以填写申请资料” ≠ “可以浏览所有正式供应商敏感资料”。**

印绣花/洗水跟单可以：

- 填写自己新增申请中的合同/收款资料。
- 查看自己提交的申请。
- 修改自己被退回的申请。

不能因此获得：

- 所有正式供应商银行账号查看权限。
- 所有正式供应商合同资料读取权限。
- 与自己申请无关的敏感字段访问能力。

技术上必须通过独立的申请接口和申请记录权限实现，不能通过放宽 `supplier_contract_data:read` 来实现。

# 12. 重复供应商防线

必须执行两次重复检查。

## 12.1 提交申请时

检查：

- 正式供应商目录
- 其他待审批申请

至少检查：

```text
标准化供应商名称 + 供应商类型
```

明确重复时阻断提交；模糊相似只提示，不自动合并。

## 12.2 审批通过前

再次检查，防止申请提交后 Root / 老板 / 生产管理已直接新增同一家供应商，旧申请再被审批造成重复。

---

# 13. 任意一人审批通过即结束

申请提交后，Root、老板、生产管理都可看到同一申请。

例如老板先审批：

```text
锁定申请
↓
确认仍为 pending_approval
↓
重复供应商复核
↓
正式创建供应商
↓
写审批记录
↓
状态 = approved
↓
关闭其他审批人的同一待办
```

之后生产管理再点时，只提示：

```text
该申请已由 XXX 于 15:32 审批通过
```

不能再次创建供应商。

---

# 14. 并发与幂等要求

审批接口必须具备：

- `expectedVersion`
- 数据库事务
- 行级锁 / 等价并发控制
- idempotency key
- 正式目录重复检查
- 审批状态二次验证

同一申请并发通过时，只能产生一个正式供应商。

# 18. 审批通过事务

“通过”必须在同一事务内完成：

```text
锁定申请
↓
校验 expectedVersion
↓
确认状态仍为 pending_approval
↓
重新检查重复供应商
↓
调用现有正式供应商创建逻辑
↓
生成正式 supplier_id / version
↓
写审批记录
↓
申请状态改为 approved
↓
绑定 approved_supplier_id
↓
关闭同一申请其他审批待办
↓
提交事务
```

中间任何一步失败，整体回滚。

# 25. UI 统一细则

- 不增加大面积无意义白框。
- 标题区靠近内容。
- 资料维护顶部操作不超过一行。
- 申请状态使用小型状态标签。
- 不给每个字段独立套卡片。
- 详情按基础资料 / 合同收款 / 工艺产能三段分区即可。
- 直接新增、提交申请使用蓝底白字主按钮。
- 通过使用轻量绿色状态/按钮。
- 退回使用红色文字或轻量危险按钮。
- 查看、编辑、批量录入保持紧凑。
- 移动端使用单列布局、16px主字号，不把桌面表格硬压缩到手机。

# 26. 施工红线

严禁：

- 跟单直接写正式供应商，再让老板“确认”。
- 只隐藏前端按钮，不做后端权限。
- 老板/生产管理只有审批权、没有直接维护权。
- 印绣花跟单因为申请能力而获得所有正式供应商敏感字段。
- Root / 老板 / 生产管理三人串行审批。
- 一人通过后其他人还能重复审批。
- 审批人直接修改原申请而不留痕。
- 申请通过后创建第二套平行供应商资料。
- 通过申请时先创建供应商、后改申请状态的非事务实现。
- 批量导入绕过正式资料权限。
- `system_admin` 因技术角色获得业务供应商维护权限。

# 27. Gate 与 Review

三个 PR 均使用 **FULL Gate**。

原因：权限变更、schema/migration、审批状态机、审计、幂等、Todo 联动、正式业务数据写入。

Codex：

- 每 PR 最多 1 次 Review。
- Gate 全绿 + intended head 冻结后再 Review。
- Review 只做审查，不默认让 Codex 编码。
- Review 发现问题由当前施工窗口修复。

# 28. 最终验收标准

## 业务侧

- Root、老板、生产管理可以直接维护正式供应商。
- 跟单、印绣花跟单可以快速申请新增供应商。
- 一个审批人通过即可生效。
- 无重复供应商污染。
- 审批和退回历史完整。
- 正式供应商进入现有外发、选厂、合同流程，无第二套数据。

## 权限侧

- 正式维护权限没有泄露给跟单。
- 申请权限没有泄露给普通角色。
- 印绣花跟单未因此获得全量敏感字段。
- system_admin 不获得业务写权限。
- 前端与 API 权限一致。

## 数据侧

- 申请版本不可被覆盖。
- 审批记录不可丢。
- 并发审批只产生一个正式供应商。
- 正式供应商创建和申请通过必须事务一致。
- 所有操作保留真实操作人和时间。

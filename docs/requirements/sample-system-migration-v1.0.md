# **1. 项目目标与冻结边界**

本项目的目标不是重新设计一套样衣业务，而是在不丢失正式服务端数据和有效业务记录的前提下，将既有样衣功能安全迁入现平台，并消除旧系统的前端通行码、前端权限判断、整库JSON写入和独立登录等风险。

## **1.1 一期范围**

- 样衣主档、批量录入、图片和采购小票；

- 首次直接领用、在库后的再次借出、归还和扫码交接；

- 出售、赠送、报废、遗失赔偿及处置审批；

- 在管样衣、待确认、已处置、库存金额及详情历史；

- 角色权限、字段级数据保护、全局我的待办和操作审计；

- 服务端正式数据、历史日志、附件元数据和在途状态迁移；

- 电脑端与移动端统一UI、响应式布局和共享分页。

## **1.2 明确不纳入一期**

- 浏览器localStorage中的本地数据；

- 新旧系统长期双写；

- 样衣与返工、外发、ERP订单的深度联动；

- 扫码盘点、标签打印、复杂BI、离线模式等新增能力；

- 对现有返工与外发业务状态机的任何修改。

## **1.3 基座不动产**

| **基座**     | **冻结规则**                                                                      |
|--------------|-----------------------------------------------------------------------------------|
| 现平台主分支 | 历史样衣批次以当时最新main为基线；当前施工基线按根AGENTS和本次授权目标远端SHA。不得从旧样衣仓库复制平台壳、认证、CSS或权限实现。 |

## **4.1 待办接收规则**

- 借出确认、归还确认发送给全部样衣行政；任一行政完成后，其他人的同一任务同步完成。

- 处置审批发送给全部有效老板和样衣审批人；同一人兼任两者只收一条待办，任一审批完成后同步结束。root可处理，但不因root身份自动接收。

- 遗失审批通过后进入待赔付；付款截图由行政上传并确认结案。

- root不会仅因管理员身份接收行政借还待办；若root同时属于老板身份，则接收老板审批待办。

# **5. 样衣状态模型**

| **状态**                    | **含义**                                             | **允许的下一步**                               |
|-----------------------------|------------------------------------------------------|------------------------------------------------|
| 借出中                      | 样衣由设计师或老板持有；新样衣建档后的初始状态。     | 发起归还；行政发起报废或遗失；符合条件时处置。 |
| 归还待确认                  | 持有人已发起归还，等待行政收到实物并扫码确认。       | 确认后在库；撤销后回借出中。                   |
| 在库                        | 样衣已由行政接收并记录存放位置，可再次借出。         | 发起借出；行政/老板/root发起处置。             |
| 借出待确认                  | 使用人申请借用，等待行政实物交接和扫码确认。         | 确认后借出中；撤销后回在库。                   |
| 处置待审批                  | 出售、赠送、报废或遗失申请等待老板/root处理。        | 批准后按类型进入终态或待赔付；拒绝后回原状态。 |
| 遗失待赔付                  | 老板/root已确定赔偿金额，等待付款证明。              | 行政上传付款截图后进入已遗失（已赔付）。       |
| 已出售/已赠送/已报废/已遗失 | 不可再借还的处置终态。                               | 仅允许查看、更正说明或root归档。               |
| 已归档                      | 逻辑作废，不参与正常列表和金额统计，但历史永久保留。 | root恢复或继续保留。                           |

| 在库        | 发起借出               | 设计师/老板            | 借出待确认                     |
| 借出待确认  | 扫码确认交付           | 行政                   | 借出中                         |
| 在库/借出中 | 发起处置               | 行政、老板或root按规则 | 处置待审批                     |
| 处置待审批  | 批准普通处置           | 老板/root              | 对应处置终态                   |
| 处置待审批  | 批准遗失并填写金额     | 老板/root              | 遗失待赔付                     |
| 遗失待赔付  | 上传付款截图并确认     | 行政                   | 已遗失（已赔付）               |

# **6. 详细业务规则**

## **6.1 新增与批量录入**

只有财务和root可以新增或批量录入。建档是“主档创建＋首次领用”一个原子事务；任何一部分失败都不得留下半条数据。

| **字段**               | **规则**                                                                |
|------------------------|-------------------------------------------------------------------------|
| 样衣编号               | 服务端生成并设置唯一约束；保留既有YI-YYYYMM-####格式及历史编号。        |
| 品牌、样衣名称、颜色   | 必填。                                                                  |
| 款号、类别、尺码、备注 | 保持旧系统可选；后续可按业务使用情况调整。                              |
| 采购人、初始持有人     | 分别绑定平台用户ID，允许不同，默认相同；展示名称只作快照。              |
| 部门、采购日期         | 必填；采购日期不得晚于当前日期。                                        |
| 采购价                 | 必填，使用精确金额字段；财务可留痕更正。                            |
| 采购小票               | 必填；批量录入可将同一张小票绑定到同批多件样衣。                        |
| 初始状态               | 直接借出中；借出用途固定记录为“采购后直接开发/打板”，不经过在库和扫码。 |

## **6.2 后续借出**

- 只有在库样衣可以发起后续借出。

- 全体设计师和老板可以发起；借用人默认当前登录人，不允许用姓名文本冒充其他人。代他人申请必须明确选择平台用户并留下代办记录。

- 借用用途必填；预计归还日期不设置、不校验、不提醒。

- 行政完成实物交付后扫描申请人的平台二维码确认；确认身份使用稳定用户ID，不以同名文字匹配。

- 确认成功后清空在库位置，生成新的借出记录并进入借出中。

## **6.3 归还**

- 只有当前持有人可以发起本人所持样衣归还；root可代操作。

- 发起归还时至少上传1张当前样衣照片，用于记录归还时实物状态。

- 行政实际收到样衣后扫码确认，并必须填写在库位置。

- 确认后关闭当前借出记录并进入在库；行政未确认前仍视为持有人保管。

- 批量归还允许逐项成功/失败，但每项必须返回明确结果并具有幂等保护。

## **6.4 处置**

| **类型** | **可发起状态**       | **发起人**                | **必填证明**                     | **审批/结案**                           |
|----------|----------------------|---------------------------|----------------------------------|-----------------------------------------|
| 出售     | 在库；借出中须先归还 | 行政；老板/root可直接发起 | 买方、出售金额、交易截图         | 老板/root审批后已出售                   |
| 赠送     | 在库；借出中须先归还 | 行政；老板/root可直接发起 | 接收对象、赠送证明照片           | 老板/root审批后已赠送                   |
| 报废     | 在库或借出中         | 行政；老板/root可直接发起 | 报废原因、具体实物照片           | 老板/root审批后已报废                   |
| 遗失     | 借出中               | 行政；老板/root可直接发起 | 责任人、遗失说明；赔付后付款截图 | 老板/root定价审批；行政确认付款后已遗失 |

**处置申请人与审批人允许为同一人：**老板或root可以自行发起并自行审批。业务审批能力授予老板、样衣审批人和root；样衣管理员、样衣财务、设计师及普通system_admin均不得审批。

## **6.5 遗失赔偿**

- 行政发起时选择遗失责任人，系统默认带出采购价作为参考赔偿额。

- 行政无权修改最终赔偿金额；老板/root在审批时填写大于0的最终金额。

- 批准后进入“遗失待赔付”，不能提前计入回收金额。

- 责任人付款后，由行政上传付款截图并确认结案。

- 遗失在业务上独立于出售，但财务结果共同计入处置回收金额，并分别显示“出售回款”和“遗失赔偿”。

## **6.6 撤销、更正与归档**

| **事项** | **规则**                                                                            |
|----------|-------------------------------------------------------------------------------------|
| 撤销     | 发起人在确认/审批前可以撤销；行政或root可因实物异常撤销，必须填写原因并回到原状态。 |
| 基本资料 | 样衣管理员与样衣财务可修改非财务主档，位置仍仅由样衣管理员维护；必须记录修改前后值及原因。                                    |
| 财务资料 | 样衣财务与root可修改采购价、追加小票，必须填写原因；财务不得撤下原小票。root可显式更正有效小票集合，但原附件与审计永久保留。                    |
| 老板权限 | 老板可填写审批相关出售/赔偿金额，但不拥有日常主档修改权。                           |
| 删除     | 禁止物理删除；root只能逻辑归档，记录仍可审计和恢复。                                |
| 附件删除 | 不得只删数据库元数据而遗留不受控对象；按平台附件生命周期执行。                      |

## **7.1 数据不变量**

- 同一件样衣只能存在一个当前状态和一个当前持有人；在库时必须有位置且不得有当前持有人。

- 同一件样衣同一时刻最多存在一条有效借还或处置请求。

- 样衣编号唯一并由服务端分配，不能由前端扫描列表生成。

- 金额使用精确十进制字段；采购价、出售金额、赔偿金额不得用浮点数。

- 所有人员关系保存平台用户ID和当时名称快照，权限判断只使用ID与能力。

- 所有写操作带幂等键和版本检查，重复点击不得产生重复借还或处置。

# **8. 数据迁移与切换**

正式迁移源为生产服务器端JSON及其引用的OSS对象；浏览器本地存储明确不迁移。生产盘点只读进行，不在盘点阶段修改旧数据。

1.  生成不可变源快照：JSON文件、文件哈希、记录数量、更新时间及OSS对象清单。

2.  清洗和映射：统一历史状态；将人员姓名映射到平台用户ID；重名、离职或无法确认记录进入异常清单。

3.  执行可重复迁移：每条记录保留旧ID和迁移批次；重复运行不得产生重复数据。

4.  核对主档与历史：按状态数量、当前持有人、借还记录、处置类型、采购金额和回收金额分别对账。

5.  核验附件：检查对象是否存在、类型和大小是否有效；缺失对象必须单独列明，不能静默跳过。

6.  处理在途任务：迁移业务状态，旧二维码和内存会话全部作废，在平台重新生成待办和确认入口。

7.  正式切换：短暂停止旧系统写入，执行最终增量与对账；通过后开放新入口，旧系统转只读。

## **8.1 对账硬门槛**

| **对账项** | **通过条件**                                                   |
|------------|----------------------------------------------------------------|
| 样衣主档   | 旧服务端有效记录与新系统迁移记录逐条可追溯；异常均有处理结论。 |
| 状态       | 各状态数量一致；旧DISPOSED等历史值完成有记录的归一。           |
| 借还历史   | 当前持有人与最后一条有效借还记录一致。                         |
| 金额       | 采购总额、在管原值、处置原值、出售回款、遗失赔偿分别一致。     |

| 待办       | 在途业务状态保持，旧确认入口失效，新平台任务可完成。           |

**任何核心对账不通过都不得开放新系统写入。**新旧系统不长期双写；若切换失败，撤下新入口并恢复旧系统写入，保留全部迁移日志。

- 列表接口必须服务端分页，只返回当前15条及真实总数；禁止为翻一页加载完整数据库。

# **14. 上线、观察与回滚**

1. 预演：在非生产环境至少执行两次相同迁移脚本与完整对账。

2. 冻结：正式切换窗口将旧系统改为只读，保存JSON、数据库和附件清单快照。

3. 迁移：执行最终导入，生成差异报告；核心差异未清零不得继续。

4. 分阶段开放与验收：先完成页面、接口和代码验证；负责人发出下一步指示后，在独立验收环境提供完整可写入口，先由 Root 使用 TEST 样衣跑通建档、借还、处置、赔付、维护及归档恢复，修复复测后再交普通业务角色验收。验收环境必须使用独立数据库、附件空间及测试配置，与生产数据和真实通知投递隔离；其可写状态由验收环境的测试初始化设置，不调用生产 cutover，也不伪造 UAT 通过证据。历史编写时该环境尚未建立；当前可测试状态须据本次真实环境、版本及回执判断，不重复创建已经验证的环境。完成相同待发布版本的真实验收后，生产才引用最终验收证据执行一次正式启用；旧系统保持只读，核心对账与备份恢复门槛保留。

   生产写入开关是全局开关，不是 Root 测试模式。`businessUatEvidence` 必须引用已完成的 Root 与普通角色验收结果，包括版本、环境、执行时间、结论和问题复测记录，不能填写测试准备代替通过证据。现有 cutover 在已开启时直接返回，不追加证据；测试写入也可能触发重新对账或导入版本保护，因此禁止将生产 enable 用作临时测试开关，禁止依靠关闭再开启补录验收。若以后需要直接在生产分阶段试用，须先另行实现并验证独立测试阶段及最终验收留痕能力，本 PR 未提供该能力。

   历史阶段授权说明（不作为当前施工暂停令）：当时仅授权功能完善及代码验证，未开放写入或 Root 实单测试。当前按最新明确任务授权执行；生产写入、真实业务数据与正式 cutover 仍须遵守上面的安全及验收条件。

5. 观察：旧系统保持只读，用于历史核对；新系统持续监控错误、待办和附件。

6. 回滚：若出现数据缺失、权限越权、状态无法推进等P0问题，撤下新入口并恢复旧系统写入。

# **16. 变更管理原则**

本文件冻结的是不可逆或高风险基线：身份、权限、数据源、状态主链、财务口径、UI金标准和上线门槛。非关键文案、字段顺序、轻微交互与后续增强不阻塞一期施工，可在真实使用中按独立需求迭代。

| **变更类型**                             | **处理方式**                                               |
|------------------------------------------|------------------------------------------------------------|
| 安全、权限、数据丢失、金额口径、状态闭环 | 必须先更新本定稿并明确批准，再施工。                       |
| 页面文案、字段排序、非关键展示           | 按现平台金标准直接优化，记录在PR说明，不反复中断业务确认。 |
| 新增业务能力                             | 进入二期需求池，不夹带进迁移PR。                           |
| 生产数据异常                             | 列入迁移异常清单；只处理具体异常，不重新讨论整套方案。     |

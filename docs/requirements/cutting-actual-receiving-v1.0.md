# 订单开裁与实裁收货联动业务规则 V1.0

**状态：已批准，按四个串行PR施工**  
**批准日期：2026-09-18**  
**适用仓库：** `lizhonghao31-crypto/dx-rework`

## 1. 业务目标

以外发订单为源，按款建立裁床任务，后续登记士啤片和实裁数；登记完成的正式款号再供仓库检索并自动关联收货。回货看板最终只增量展示实裁数与裁床登记人/时间。实裁暂不参与新增回货差异、判责、扣款或审批。

## 2. 固定业务边界

- 一级模块为“订单开裁”，二级本期仅“裁床实裁”；不提前建设裁床计划。
- 外发老板批准后自动按源款明细建立裁床任务，不等待财务核对，也不让裁床重新建单。
- 一款一个登记项；稳定内部身份为 `sourcing_case_id + position`。完整正式款号是业务识别码，后四位只用于搜索，代用号不是正式款号。
- 老板批准后、合同生成成功后仍按外发原入口补改正式款号；裁床任务沿用原稳定行，不因补号、合同换版、重试或转厂重新创建。
- 士啤片与实裁数分别记录，无固定换算；实裁数为实际发出且可制作成衣的件数。
- 实裁对应款合同数量±5%为正常边界，超过只标记、不阻断提交、不新增审批。
- 裁床主管与裁床工人均可初次登记；提交后普通人员不可覆盖，Root纠错必须留痕。
- 已裁且具有有效正式款号后才进入仓库正常候选；仓管不重复填写实裁。
- 本期不做分批裁剪、多人上数汇总、补裁损耗自动抵扣、二次工艺全流程、裁床工资、外厂账号、新待办或额外审批。

## 3. PR01 数据基础

PR01只建立源单基础，不开放尚不能办理的菜单或收货新链路。

- `cutting_orders`：老板批准事务内按每个源款创建一条，唯一键为 `sourcing_case_id + sourcing_line_position`。
- 创建与批准快照位于同一事务；任何裁床任务建立失败都会使本次老板批准整体失败，不能出现“批准成功但裁床漏单”。
- 任务保存初次批准快照作为来源审计，但展示当前正式款号时读取 `current_sourcing_case_lines.formal_style_no`；代用号只保留识别，不冒充正式号。
- 正式款号修订读取当前视图，因此只更新显示身份，不新建任务、不改变数量、审批和历史关联。
- 历史已批准订单不在本迁移中自动补任务，也不伪造裁片/实裁事实；生产历史接入必须另获生产操作授权。

## 4. PR01权限

新增角色：
- `cutting_supervisor`：裁床主管。
- `cutting_worker`：裁床工人。

新增能力：
- `cutting:orders:view`：裁床基础记录读取。
- `cutting:records:create`：后续PR02用于初次登记。

裁床主管、裁床工人获得两项能力；老板、生产管理、订单跟单仅获得本期裁床基础读取能力。订单跟单只读本人源单。Root保留平台既有超级用户能力。仓管、板房主管、板房工人及其他角色不因本轮自动获裁床能力。迁移不向任何真实员工自动赋角色。

## 5. 安全字段白名单

PR01安全投影只返回款号身份、款式/颜色/性别、对应款数量、加工厂、跟单、交期、裁床方式和批准时间等裁床必要事实。不得返回预算价（原达兴价格）、IE价格、外发价格、金额、利润/成本、调价说明、付款/银行资料或合同附件。

## 6. 后续PR边界

- PR02：裁床列表/详情、双数量登记、±5%提示、Root纠错、正式款号候选资格。
- PR03：仓库按正式款号选单、首收/补录/多次收货自动关联，并停用旧生产发货二次选单。
- PR04：回货卡片增加实裁和裁床登记人，完成端到端与多尺寸验收。

## 7. 回退与历史事实

数据库变更为增量添加。回退优先回到仍能读取新增字段的兼容代码，不DROP裁床表、不删除已登记事实。PR01没有生产历史补建、真人角色赋权、生产数据修改或测试数据清理授权。

## 2026-09-18 PR02 实裁登记落地约定

- 初次登记事实写入 `cutting_records`，每个裁床任务仅一条；士啤片与实裁数均为非负整数，0 为真实数值，空值不能提交，两者无换算关系。
- 已提交后普通裁床人员只读；Root 修正写入 `cutting_record_corrections` 追加版本，不覆盖初始登记人、登记时间和原始数值。
- 有效读取通过 `current_cutting_records` 取得最新数量；±5%使用原始整数精确比较，边界包含，超范围仅提示。
- 实裁登记必须已有当前正式款号；仅代用号的待补号任务可以查看但不能登记。补号仍走外发原入口。
- 仓库候选资格通过只读视图 `current_cutting_style_options` 动态发布：源业务有效＋已登记＋当前正式款号。正式款号后续合法修订时沿用同一裁床任务和实裁事实，不复制数量。
- 列表搜索与分页由服务端完成；搜索款号、合同编号、加工厂、跟单、登记人，后四位属于普通子串检索。有冲突的正式款号只标记冲突数量，后续仓库不得自动猜选。
- 页面仅展示裁床所需白名单：款号、款式/颜色/性别、合同编号、对应款合同数量、加工厂、跟单、交期、裁床方式、工艺、获准产品图片和实裁事实。价格、金额、调价、付款与合同附件不进入裁床响应。
- 初次登记与 Root 修正都必须在写入事务中锁定并校验源外发单仍有效；Root 逻辑删除源单后，任何旧页面不得继续追加实裁事实或修正。
- 初次登记和 Root 修正均使用幂等键；同一请求体发生网络重试时复用原 key，避免“已成功但响应丢失”被误判为版本冲突。

## 2026-09-18 PR03 仓库正式款号收货联动

- 仓库新收货入口只允许从“已完成实裁且当前存在正式款号”的候选中选择，稳定身份使用 `cutting_order_id`。仓管输入正式款号末尾至少4位检索后，必须点击完整候选，不能自由填写、不能用代用号冒充正式款号。
- 候选仅向 `receiving:create` 仓管投影收货所需字段：正式款号、颜色、加工厂、实裁数及冲突提示；仓管不因此获得“订单开裁”模块权限。
- 首次收货、补录、嘉顺多次收货、其他工厂多次收货均写入同一稳定 `cutting_order_id`。同一收货批次一旦已有裁床稳定关联，后续多次收货不得切换到另一条裁床任务，即使款号文字相同。
- 新收货事实的款号由服务端根据裁床任务派生；客户端不再提交自由款号，也不再提交生产订单编号。历史收货事实不补造裁床关联，`cutting_order_id` 保持可空兼容。
- 旧“关联生产发货单（选填）”仓库入口停用。若所选裁床任务所属外发源单存在已发货、未排除且启用生产试点的生产订单，系统在同一收货事务中自动建立生产回货关联；不存在符合条件的生产发货单时不阻断仓库收货。
- 自动生产回货关联只替代仓管二次选单，不停用实时生产看板、生产进度填报、风险判断、未更新提醒、待办或历史回货摘要。
- 正式款号存在多条已裁候选时，系统展示加工厂/颜色等上下文并要求仓管明确点选，不自动猜选。

## 2026-09-18 PR04 订单回货看板实裁事实展示

- 回货看板新收货数据以 `cutting_order_id` 作为读模型分组身份；历史没有裁床关联的数据继续按标准化款号聚合，不补造裁床事实。
- 数量层固定顺序：`实裁数 | 送货单数量 | 实收 | 次品 | 收货差异 | 装箱数量 | 装箱差异`。实裁缺失显示 `—`，已登记 0 必须显示 0；实裁仅展示，不进入收货差异、装箱差异、判责、扣款或KPI公式。
- 人员层在原款号/状态与收货人之间增加“裁床登记人”；显示最初登记人和最初登记时间。Root修正实裁后数量显示当前有效值，但原登记人/时间不被覆盖。
- 同正式款号存在多条已裁任务时，看板必须保留为独立行；多次收货展开状态也按当前行稳定身份保存，不能因款号相同联动展开。
- 宽卡数量区为7列；卡片可用宽度小于840px时切为4+3：第一行实裁/送货单/实收/次品，第二行收货差异/装箱数量/装箱差异，其中装箱差异占余下两列。
- 不新增实裁KPI、实裁差异、实裁判责或新的卡片模块；原收货、装箱、差异处理、返工入口和Root修正能力保持。

## 2026-09-18 开裁1.1 PR01 历史批准订单接入

- 0197 原始上线明确不补历史任务；开裁1.1 经业务负责人批准后，以新增迁移补齐历史已批准外发订单，不改写已执行迁移。
- 补入范围仅限未逻辑删除且存在真实老板批准快照的外发订单；每个批准款色行按 `sourcing_case_id + sourcing_line_position` 补一条缺失的裁床任务。
- 同一订单存在多次批准快照时，缺失任务使用最新批准快照作为来源审计；已经存在的裁床任务保持原任务 ID、原批准来源和全部实裁事实，不更新、不复制。
- 回填只创建任务身份，不写 `cutting_records`，不把合同数量、送货数量或任何其它历史数量冒充士啤片/实裁数。
- 已逻辑删除、没有老板批准快照或批准数据无法满足既有外键/守卫约束的订单不得猜造任务。
- 迁移必须可重复执行；与新审批链同时存在时依赖现有唯一键防止重复任务。
- 历史任务补入后继续遵守现有规则：有正式款号才可登记实裁，完成实裁后才进入仓库候选。
- 裁床实裁列表分页在桌面端以整个列表宽度为基准居中；移动端统计可独立占行，但页码仍居中。该调整不得修改共享分页组件或其它模块版式。



## 2026-09-19 裁床登记优化

- 裁床页面用户可见名称统一为“士啤片”；底层 `piece_count / pieceCount` 数据字段保持不变，不迁移、不重算历史数量。
- 初次实裁登记必须同步上传“裁床单”：最少1张、最多3张，支持 JPEG、PNG、WebP；上传控件、缩略图、移除和图片兼容链路复用返工成熟图片上传能力。
- 裁床单图片与初次 `cutting_record` 同一事务绑定，属于该次登记事实；图片未完成上传、归属不符、格式不符、缺图或超过3张均不得提交登记。
- 历史已登记记录不补造裁床单；新增约束只作用于本规则生效后的新登记。
- 登记完成后普通裁床人员只读裁床单，不允许删除、替换或重新绑定；Root数量修正不改变原裁床单。
- 裁床主管、裁床工人均可按原 `cutting:records:create` 权限上传并提交，不新增审批节点或额外角色。


## 2026-09-19 仓库款号过渡兼容规则

- 当前仍存在未进入裁床正式款号数据库的历史订单，因此仓库收货暂时采用“搜索辅助、自由输入兜底”，不实行“必须命中裁床款号才能提交”。
- 普通收货与补录：输入完整正式款号若唯一精确命中已裁候选，前端自动选中并写入 `cutting_order_id`；输入末尾至少4位时继续展示候选供仓管点选。
- 搜索没有命中时，不显示“未命中”“历史款号”“未关联实裁”等额外提示，不增加二次确认；仓管可以直接按输入款号正常提交，后台保持 `cutting_order_id=NULL`，不得伪造裁床任务或实裁数。
- 多次收货继续必须先找到已有收货批次；历史自由输入批次允许继续追加收货，不要求补造裁床关联。已有 `cutting_order_id` 的批次沿用原关联，不得切换到另一条裁床任务。
- 完整款号搜索只是辅助识别：唯一精确命中时自动选中；存在多个精确候选时不得自动猜选。
- 当前生产服务显式开启 legacy 款号输入兼容。待历史未入库订单基本收完后，再单独关闭该兼容开关，恢复“必须命中正式款号候选才能创建新收货”的严格模式；本期不设自动截止日期。

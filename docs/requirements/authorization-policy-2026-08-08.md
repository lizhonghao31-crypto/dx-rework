# 返工系统权限规则变更记录（2026-08-08）

本文件是 `startup-requirements-v1.2.md` 之后已确认的权限变更记录。发生冲突时，本文件仅在权限模型范围内覆盖 v1.2 的旧描述；业务流程、金额、状态与多人独立确认规则仍以需求基线及后续已确认变更为准。

## 1. Root / 超级用户

- 李俊岳为当前系统唯一 Root 身份。
- Root 不是可在角色下拉框中授予的普通业务角色，而是绑定稳定钉钉身份并由首位老板 bootstrap 不可变记录锚定的系统最高授权身份。
- 服务器私有 `ROOT_DINGTALK_USER_ID` 必须与已锁定 bootstrap 身份一致；不一致时服务不得启动。
- Root 可以进入全部业务页面和技术管理页面，并在需要时以明确的业务 acting role 执行人工操作；审计记录必须保留 `root_superuser` 身份。
- Root 不能绕过历史不可变、已锁定事实不可改、本人不得批准本人发起的历史调整、高倍率需独立另一老板确认等硬业务完整性规则。

## 2. 受保护角色

受保护角色为：

- `owner_group`（老板）
- `system_admin`（系统管理员）

规则：

- 只有 Root 可以授予或撤销受保护角色。
- 普通老板不能授予或撤销任何人的老板/系统管理员角色。
- 普通系统管理员也不能授予或撤销老板/系统管理员角色。
- 非 Root 不能停用或恢复持有老板、系统管理员或 Root 身份的账号。
- Root 不能停用自己，也不能撤销自己的受保护角色。
- 即使某个非 Root 用户同时拥有 `owner_group + system_admin`，也不成为 Root。

## 3. 老板 `owner_group`

老板是最高业务权限角色，不是技术管理员。

老板拥有：

- 全部业务事实和业务页面读取准入；
- 管理 Dashboard、现场 Dashboard、业务明细及报表；
- 责任判定、责任接管、本厂承担审批及需求明确赋予老板的管理动作；
- 审计日志读取；
- 业务基础资料维护；
- 普通业务角色的授予和撤销；
- 员工权限管理页面准入。

老板不因角色本身获得：

- `system_admin` 技术异常处置能力；
- 受保护角色分配权；
- 绕过独立确认、自批限制或历史不可变规则的能力。

## 4. 系统管理员 `system_admin`

系统管理员是技术管理角色，不是业务超级用户。

系统管理员拥有：

- 系统管理后台读取；
- 技术异常的受控、幂等重试；
- 审计日志读取；
- 后续明确实现的系统级配置与集成维护能力。

系统管理员不自动拥有：

- 管理 Dashboard 或业务全量查看；
- 工资、责任、扣款、本厂承担等业务操作；
- 业务基础资料维护；
- 员工业务角色管理；
- 代理授权管理；
- 老板或系统管理员角色分配权。

## 5. 普通业务角色管理

- Root 和老板可以管理普通业务角色。
- `system_admin` 不负责普通业务角色体系。
- 一人可以同时拥有多个普通业务角色。
- 角色变更、账号停用/恢复必须记录操作人、原因和审计事件。

## 6. 唯一直接接收岗位

以下岗位在当前一期业务中按一个稳定直接接收人路由；任意时刻最多存在一个未撤销角色绑定：

- `tail_supervisor`
- `ie_reviewer`
- `production_management`
- `embroidery_washing_merchandiser`
- `factory_payables`
- `embroidery_washing_payables`
- `fabric_payables`
- `administrative_clerk`
- `wage_month_close_accountant`

换人时必须先撤销旧角色，再授予新人员。需要临时替代时使用系统已经设计的受控代理/转交机制，不通过同时增加第二名直接接收人实现。

以下角色明确不采用该唯一限制：

- `quality_control`
- `worker`
- `order_merchandiser`
- `finance_read`
- `owner_group`
- `system_admin`

## 7. 分层鉴权规则

同一业务动作的权限必须在以下层级保持一致：

1. 前端页面/按钮准入；
2. HTTP Route 身份和 acting role 构造；
3. Service 业务动作校验；
4. PostgreSQL 触发器/函数及不可变审计约束；
5. Todo 接收人路由。

前端隐藏按钮不构成安全边界。后端和数据库必须能够独立拒绝未授权操作。

## 8. Root 单人 UAT 的 Todo 例外

为了在真实测试账号尚未配置齐时先验收底层状态机，Root 发起的业务动作允许在“唯一待办接收人尚未配置/当前不可唯一路由”时跳过该次待办投影，不回滚已验证的业务状态变更。

该例外：

- 只对 `root_superuser` 生效；
- 只覆盖接收人可用性/唯一性冲突；
- 不对普通业务用户生效；
- 不覆盖高倍率独立老板确认等明确要求第二人的规则；
- 不吞掉任意数据库、状态、金额或业务校验错误。

真实钉钉待办送达、角色隔离和多人独立确认必须在多人 UAT 中补验。

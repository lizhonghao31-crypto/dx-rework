# 网页版 ChatGPT Work 施工流程 v2.0

状态：长期有效  
适用仓库：`lizhonghao31-crypto/dx-rework`  
更新日期：2026-09-10

本文件只描述执行流程；长期红线和业务来源以根目录 `AGENTS.md` 为准。

## 1. 默认分工

当前 ChatGPT Work/助手是默认控制器和执行器，负责方案、施工、定向验证、PR 修复和交付。Codex 默认仅做独立 Review；除非业务负责人对当前任务明确要求 Codex 编码，否则不得调用 Codex 施工。

## 2. 唯一施工流程

1. 读取 `AGENTS.md` 与本次唯一相关业务 Golden Source。
2. 一次性核验最新 `main`、相关开放 PR、当前 Head；冻结 scope 和 Gate 等级。
3. 在本地/当前工作区先完成定位、完整修改、定向测试和最终 diff 审查。
4. **全部准备好后再一次性 push intended Head。**
5. 创建 PR 时使用 `[QUICK]` 或 `[FULL]` 标题前缀；二者只能选一个。
6. CI 异步运行。没有失败/Review 新事实时不重复核验，不原地盲等。
7. Gate 失败时先读精确日志，确定根因，集中修复后再形成下一 Head；禁止连续小 push 调试。
8. 所需 Gate 全绿且代码冻结后，才判断/执行 Codex Review。
9. Review finding 由当前助手核验并修复；不默认交给 Codex 编码。
10. 达到当前任务授权下的交付条件后，直接给出“可以合并”或“不能合并 + 唯一阻塞”。

## 3. 两种推进模式

### 逐 PR 验收
当前 PR 达到可合并状态后等待业务负责人确认，再开始下一 PR。

### 全程接手
业务负责人明确授权后，助手在授权范围内连续完成施工、门禁、Review 修复及获授权的合并；普通可处理阻断不得导致无故停工。

两种模式都不改变生产数据、密钥、Root 边界等安全红线。用户说“停”立即停止。

## 4. Gate 分类

### QUICK
适用于纯文档、低风险文案/CSS、隔离测试维护以及未改变接口、状态、权限、数据口径的小修改。

### FULL
适用于 migration/schema、权限身份、财务金额数量合同、核心状态机/审批/审计/幂等、跨模块关键链路、部署/Actions/基础设施、共享平台能力、P0/P1。

PR 创建前必须完成分类：
- `[QUICK]` 只允许 Quick Gate；
- `[FULL]` 只允许 Full Gate，Quick Gate 必须跳过。

当前 Head 变化后，只认新 Head 的 Gate 证据。

## 5. Push 纪律

- GitHub Remote 不是调试器。
- 已知未完成的配套修改不得分批 push。
- 代码 + 测试 + migration + manifest 等属于同一修复时，一次准备完整后提交。
- Gate 运行中不继续“顺手改”；只有真实阻断已经定位并完成集中修复时，才更新 Head。
- 同一 Head 的失败 Job 最多 rerun 一次；再次失败先修根因。
- 禁止 noop commit。

## 6. Codex Review

Codex Review 是审查渠道，不是施工渠道。高风险 PR 默认需要独立 Review，低风险 PR 可不请求；具体按当前任务授权执行。

默认最多一次 Review；真实 P0/P1 修复或业务负责人明确授权时才允许第二次。Review 之后仍由当前助手负责修复。

## 7. 汇报格式

用户问“可以合并了吗？”时，只回答：

- `可以合并`；或
- `不能合并：<唯一具体阻塞>`。

用户问进度时，报告：已完成、当前真实状态、剩余步骤。不要用 SHA、内部路径、重复日志淹没业务负责人，除非版本错配本身就是阻塞。

## 8. ECS 维护

多步骤高风险维护命令必须使用独立脚本执行，不能把可能 `exit` 当前 Shell 的脚本体直接粘贴到登录会话，也不能 `source`。Acceptance 更新只做与当前 diff 对应的最小操作，不在 ECS 上运行 CI/Full Gate。

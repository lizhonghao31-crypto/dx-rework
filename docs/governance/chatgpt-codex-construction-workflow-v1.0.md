# ChatGPT + Codex 施工流程 v1.0

状态：已确认  
生效日期：2026-08-26  
适用仓库：`lizhonghao31-crypto/dx-rework`

## 1. 目的

本流程把跨聊天窗口必须延续的施工约定固化在仓库中。聊天记录不是流程 Golden Source；任何新窗口或新任务都必须先读取根目录 `AGENTS.md`、本文件和当前业务路线文档。

## 2. 角色分工

### ChatGPT 控制器

- 读取 Golden Source、当前路线、GitHub `main`、现有分支和 PR。
- 冻结本次范围、允许文件、禁止文件和验收门禁。
- 选择执行方式，审查最终 diff，创建或更新 PR，并向用户汇报。
- 不得擅自触发 Codex Review、合并 PR 或部署。

### Codex 执行器

- 在任务明确、基线正确时承担编码、定向测试和提交。
- 不自行扩展范围、设计新业务规则、改变 Golden Source、触发 Codex Review、合并或部署。
- 云任务没有 remote、不能 push 或不能创建 PR，不视为项目阻塞；由 ChatGPT 控制器接管 GitHub 交付。

### 业务负责人

- 可以授权覆盖默认施工流程。
- 独占 Codex Review 的手动触发权，以及 PR 合并、部署和业务规则变更的决定权。

## 3. 每次施工的唯一流程

1. 读取 `AGENTS.md`、本文件、相关需求/ADR和当前路线。
2. 核对仓库、最新 `main`、base SHA、现有同路线分支/PR和依赖 PR 状态。
3. 输出本次目标、范围、允许文件、禁止文件、执行方式和验收门禁。
4. 选择 Codex 执行或 ChatGPT 直接施工。
5. 完成修改、定向测试和最终 diff 审查；在 PR 创建前确定本 PR 的门禁等级。
6. 创建普通 PR（`draft: false`）。
7. 若本 PR 必须执行 Full Gate，创建 PR 后立即添加 `full-gate` label，不得等待用户提醒。
8. 立即向用户报告 PR 链接、范围、已完成测试、门禁等级，以及本 PR 是否需要 Codex Review，然后结束本轮。
9. CI 异步运行，不得为了等待 CI、修改措辞、整理计划或重复确认而停留在施工窗口。

## 4. 执行方式与自动降级

默认优先使用 Codex 执行，但 Codex 不是唯一施工渠道。

出现以下任一情况时，ChatGPT 控制器自动切换为直接施工，不需要再次询问：

- Codex 额度不足或服务不可用；
- 云环境缺少目标提交、remote、push 或 PR 能力；
- HEAD 无法与已确认基线对齐；
- 环境反复初始化、明显卡住或继续等待会降低效率；
- Codex 已偏离范围，继续修正的成本高于直接接管。

自动降级要求：

- 简短告知用户已经切换执行方式；
- 继续遵守同一范围、Golden Source、测试和安全红线；
- 不因工具变化重新设计需求；
- 不把缺少 Codex 能力误报为项目无法施工。

## 5. Git 与 PR 规则

- GitHub `main` 是唯一代码基线；禁止使用旧聊天中的 SHA 猜测施工。
- 同一路线已有分支或 PR 时优先复用，禁止制造重复 PR。
- 一个 PR 只解决一个明确目标，不夹带无关重构。
- 完成施工和本地/云端可用门禁后直接创建普通 PR，禁止无理由转为 Draft。
- PR 创建后不原地等待 CI；CI 失败作为新的明确事件处理。
- 禁止通过连续 push 把 GitHub Actions 当作调试器。
- Codex Review 只能由业务负责人手动触发，ChatGPT、Codex 和其他 Agent 均不得代为触发。
- 合并和部署必须由业务负责人明确决定。

## 6. Full Gate 判断与触发

### 6.1 必须执行 Full Gate

PR 只要命中以下任一项，ChatGPT 控制器就必须在 PR 创建后立即添加 `full-gate` label，并以当前最终 Head 的成功运行作为合并前证据：

- 新增或修改数据库 migration、migration manifest、schema、数据回填或数据库约束；
- 修改登录、身份、角色、capability、数据可见范围、Root/老板特权或后端授权；
- 修改金额、单价、数量、工资、合同、付款、财务核对或结算口径；
- 修改业务状态机、审批链、审计事件、幂等、并发或不可变事实；
- 修改跨模块数据联动、待办路由、通知投影或关键业务事件；
- 修改部署、发布、环境、备份恢复、基础设施或 GitHub Actions 门禁；
- 修改共享平台壳、共享导航、共享权限入口，影响两个及以上模块；
- 修复 P0/P1、关键业务链回归，或业务负责人明确要求执行 Full Gate。

Full Gate 成功证据必须属于当前 PR 的当前 Head。任何新提交都会使旧 Full Gate 失效；label 保留时应由新 Head 自动重跑。

### 6.2 默认不需要 Full Gate

以下变更在没有触及上方高风险项时，默认只需 Quick Gate 与对应定向测试：

- 纯文档、注释、路线状态或治理文字；
- 隔离页面的文案、间距、样式微调；
- 不改变接口、状态、权限和数据口径的低风险测试维护。

无法明确判断时按高风险处理。业务负责人可以明确要求增加 Full Gate，但不得要求跳过命中的高风险门禁。

### 6.3 失败处理

- `skipped`、`cancelled`、旧 Head 成功都不算通过。
- 失败后先读取精确 job 和日志，判断代码缺陷、测试过期、环境瞬态或门禁配置问题。
- 只做根因对应的最小修复；不得删除有效测试、降低断言或盲目 rerun。
- 同一 Head 的失败 job 最多重跑一次；Head 改变后必须以新 Head 重新完整取证。
- 最终必须明确报告“Full Gate 成功”或具体阻塞，不能只说“已处理”。

## 7. Codex Review 判断与触发

### 7.1 必须请求 Codex Review

命中以下任一项时，相关 Quick/Full Gate 全绿后必须进入 Codex Review：

- 权限、身份、Root/老板特权或敏感数据边界；
- 财务、工资、金额、合同、付款或结算；
- 数据库迁移、不可逆数据影响或复杂约束；
- 核心状态机、审批链、审计、并发或幂等；
- 跨模块关键链路、P0/P1 修复；
- diff 较大、人工审查仍存在明显不确定性；
- 业务负责人明确要求。

### 7.2 默认可不请求 Codex Review

纯文档、低风险文案/CSS、隔离测试维护，以及未改变业务规则、权限、数据结构和公共接口的小改动，默认可不请求。

### 7.3 固定触发规则

- Codex Review 只能针对“最终 intended Head”：所需门禁已全绿、diff 已冻结、不再计划新增功能。
- ChatGPT、Codex 和其他 Agent 不得自行触发。控制器必须明确告诉业务负责人：“现在需要 Codex Review，请手动触发”。
- 默认每个 PR 只请求一次。只有 Review 发现 P0/P1 后发生实质修复，或业务负责人明确授权，才请求第二次。
- Review 提出问题后，先核对当前代码和权威 review thread；只修真实、未过期且属于范围的问题。
- 任何修复提交都会使旧门禁证据失效；重新通过所需门禁后，再判断是否需要第二次 Review。

## 8. PR 全绿后的固定动作与结论

“全绿”必须同时满足适用于本 PR 的全部条件：

1. 当前 Head 与远端 PR Head 完全一致；
2. Quick Gate 成功；
3. 若命中 Full Gate，当前 Head 的 Full Gate 成功且不是 `skipped`；
4. 若命中 Codex Review，Review 已完成且没有未解决的 P0/P1 或合并阻断意见；
5. PR 未落后到会使证据失效，且 GitHub 未报告冲突或不可合并。

控制器确认后必须立即给出以下两种结论之一，不得让业务负责人自行从绿色勾选推断：

- **可以合并**：给出 PR 链接、当前 Head、已通过门禁，以及是否仍需部署后 UI/UAT 验收。
- **不能合并**：给出唯一、具体、可执行的阻塞项；不得只说“还在检查”或“基本可以”。

固定顺序：

1. 若仍需 Codex Review：明确要求业务负责人手动触发，此时结论为“暂不能合并”。
2. 若 Review 不需要或已通过，且所有适用门禁全绿：明确回答“可以合并”。
3. 未经业务负责人明确决定，不自动合并或部署。
4. 业务负责人报告“已合并”后，控制器必须核验 PR 的 `merged` 状态和最新 `main` SHA，再报告本阶段是否完成及路线中的下一 PR。
5. UI PR 即使代码可合并，也必须单独说明是否还需要部署后桌面端/移动端验收；不得把 CI 全绿冒充视觉验收。

## 9. 停止、阻塞与汇报

- 用户说“停”时立即停止；不得继续检查、改 PR、等待 CI或做收尾操作。
- 遇到权限、基线、Golden Source 或业务含义冲突时，立即报告具体证据和唯一阻塞点。
- PR 已创建即视为本轮交付完成；非阻断性检查不得延迟汇报。
- 状态汇报必须区分“代码阻塞”“外部 CI 异步运行”和“非必要收尾”，不得用“还在处理”混淆。

## 10. 授权覆盖规则

本文件描述默认流程，不是不可变的业务法律。

- 业务负责人在当前任务中的明确授权可以覆盖流程性规则。
- 临时授权只对明确范围和当前任务生效，任务结束后恢复默认流程。
- 长期授权必须写回 `AGENTS.md` 或本文件并经 PR 合并后生效。
- 授权不得绕过平台安全策略、密钥保护、生产数据保护或法律合规要求。
- 若授权内容与旧流程冲突，以更具体、更新且明确的业务负责人授权为准。

## 11. 新窗口启动口径

进入新聊天窗口后，不要求业务负责人重新叙述历史。控制器应先读取：

1. 根目录 `AGENTS.md`；
2. 本文件；
3. `docs/roadmap/platform-sourcing-roadmap-v1.0.md`；
4. GitHub 当前 `main`、开放 PR 和对应 Head 状态。

读取完成后，只报告当前状态、下一步和发现的真实冲突，不重复询问已经版本化确认的问题。
